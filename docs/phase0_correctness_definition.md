## 1. このプロジェクトで「正しい結果」とは何か

MVPの目的は**2点を数字で検証する**こと（要件定義書 §6）。それ以外は範囲外。

- 正しい結果の例1: `npm run sim -- train --card running --times 20` を実行すると、
  **8回目でタイプが「バランス→ダイナモ」に変わる**。全7カードで3〜10回の範囲に収まる。
- 正しい結果の例2: 同じシードで2回実行すると、スコア・スタッツ・イベントログが
  **1件も違わずに一致**する（サーバー権威の試合処理・リプレイの土台になる）。
- 正しい結果の例3: プリセット6チームの総当たり3,000試合で、
  **全体勝率が70%を超えるチームが1つも無い**。かつ3チーム以上の間に
  「AはBに強く、BはCに強く、CはAに強い」というじゃんけん関係が実測で出る。
- 正しい結果の例4: 6チームの**特訓の回数と土台が完全に一致**している（D-43 で「能力合計の一致」から変更）。
  一点突破は伸びにくくなるので合計が少なくなる。**それが一点突破の代償**であり、差が出るのは割り振りだけ。

## 2. 「間違った結果」の具体例

- 間違いの例1: 特訓を20回繰り返してもタイプが変わらないカードがある
  → 「特訓で選手が変わる」という遊びの核が成立していない。
  （実際に発生した: マンツーマン単体／スペシャル4組。§12-#1 と D-10 で決着）
- 間違いの例2: 同じシードなのに結果が変わる（乱数のモジュール関数を使う、
  dict/set の反復順に依存する、並列実行で順序が混ざる）
  → 非同期PvPの不正検証・リプレイが不可能になる。
- 間違いの例3: 1チームが勝率90%になる／あるいは1チームが勝率10%になる
  → 「課金や時間だけでは勝てない」(GD-01/02) の検証が失敗している。
  **天井だけ見て床を見ないのも間違い**（弱すぎるプリセットを見逃す）。
- 間違いの例4: スタッツが現実離れしている（1試合で奪い合い4,000回、走行191km）
  → 数字を見たオーナーが仕様の妥当性を判断できない。
  （実際に発生した。1ティックごとに判断させていたのが原因）
- 間違いの例5: タイプを選手データに保存し、隠しパラメーターと食い違う。

## 4. ユーザーの行動想定

- ユーザーは誰か: **現時点ではオーナー自身**（MVPは画面なしのCLI）。
  将来の対象は「作戦を組むのが好きで、操作技術で勝ちたくない層」。
- 典型的な行動パターン: 定数を1つ変える → `batch` を回す → 勝率表を見る → また変える。
  この**反復の速さ**が価値なので、3,000試合が数分で終わることは要件の一部。
- 期待すること: 「特訓の違いが試合の動きと勝敗に出る」ことを、数字で納得できること。
- 絶対にやってほしくないこと: 検査が全部緑なのに、実は仕様を満たしていない状態で
  「完成しました」と報告されること。

## 8. ステータスの正しさ（D-43・2026-10-04 オーナー指示）

**オーナーの言葉**: 「本来はある程度のステータスの上に最適化されたステータスポイントの割り振りがあるはずなのに、
現状はそれ以外の全てを捨てて一点突破状態だから、バランスがおかしいのもおかしな話じゃないのかもしれない」。

### 正しい結果

- 正しい1: ピッチに立つ選手は**全員がプロの土台**を持つ（見える能力はどれも46以上。ポジションで得意が違う）。
  「スタミナ100で他は素人（40）」の選手はいない
- 正しい2: 同じカードを20回続けた選手は、その能力が**一番高くなる**が、能力の**合計は分散した選手より少ない**
  （伸びるほど伸びにくくなる）。だから「何を捨てて何を伸ばすか」に**内側の最適**がある
- 正しい3: AIチームもプレイヤーのチームも**同じ作り方**（土台＋特訓20回＋個人差）。片方だけ個人差を持たない
- 正しい4: プリセットは「得意を中心に、支える能力も育てた」割り振り（一点突破ではない）で、
  相性 [7] の勝率が全チーム30〜70%に収まる
- 正しい5: 得点・シュート・決定率・走行が現実の相場に入り、空いたゴールの半分以上はシュートまで行く

### 間違った結果

- 間違い1: 1枚のカードに全部注ぐのが常に最強（伸びが一定だと必ずこうなる）
- 間違い2: 土台が低く、特訓していない能力が素人のまま試合に出る
- 間違い3: プレイヤーのチームだけ個人差があり、それだけで構造的に勝つ（D-41 で実測: プリセット相手に 72〜77%）
- 間違い4: タイプの変わり方（3〜10回）が、伸び方の変更に巻き込まれて崩れる

### 定量の基準

| 指標 | 合格ライン |
|---|---|
| 見える能力の伸び | 69以下で+3 ／ 70〜84で+2 ／ 85以上で+1（スペシャルは1.5倍・切り捨て） |
| 隠しパラメーターの伸び | **変えない**（タイプの変わり方 D-03 を守る） |
| 土台（見える能力の合計） | フィールド全ポジション 280 ／ GK 280 |

## 9. 学習する選手AI（D-48・2026-10-05 オーナー提案）

> **承認**: オーナー（猪野凌） ← ✅ **2026-10-05 承認**（「一旦この内容でコミットしてから着手してほしい」）
> 追加の指示: 「現状のビジュアルシステムを踏襲しつつ、フィールドやＧＫの環境を1v1に調整して試してほしい。
> 今のフィールドで1v1にしてしまうと大きすぎる懸念点がある」→ S1 は**1対1用の小さいフィールド**で行い、今の画面で見られるようにする

**オーナーの言葉**: 「今の開発手法ではそれっぽさは作り出せても、それっぽさから抜け出す事は出来ないと思っています。
そこで提案したいのが、選手たちに1v1からはじめて最終的に11v11まで人数を増やしながら学習をさせていくという方針です」
／「まずはボールをゴールに入れるとそれを阻止するAIの作成からはじめて、徐々に人数を増やしつつ、各行動に報酬系を与える事で
行動を促しやすくしていく。あと、フィールドを区分けして、点数として使う機能は非常に面白いと思ってるから、それは使いたい」。

### 9.1 何を変えて、何を変えないか

| | 変える | 変えない |
|---|---|---|
| 選手の判断 | 人が書いた評価式（効用・D-41）→ **学習した方針**（重みの列） | 判断の材料に**能力と隠しパラメーターを必ず入れる**（育成ゲームの核・要件 §6） |
| 物理 | — | 走る・蹴る・奪い合い・入る確率（出典つきで合わせた式）。学習AIは同じ物理の上で動く |
| 決定論 | 学習（開発側・オフライン）は乱数も時間も自由 | **ゲームに載るのは学習済みの重みだけ**。同じシードなら同じ試合（D-08・D-16） |
| 物差し | — | 出典つきの相場・疲れ方・撃つ場所・型の個性・相性（`npm run check`・`measure`）を**学習AIの通知表**にする |

### 9.2 段階（カリキュラム）

| 段階 | 人数 | 覚えること | 次へ進む条件（オーナーの目視＋数字） |
|---|---|---|---|
| S1 | 攻め1 対 守り1（＋今のGK） | 入れる／阻止する（運ぶ・抜く・撃つ・寄せる・奪う） | 9.5 の S1 の基準 |
| S2 | 2対1 → 2対2 | 出すか自分か・受けに動く・カバー | 数的優位で攻めが勝ち越す |
| S3 | 3対3 → 4対4 | 三角形・幅・裏への走り込み | 裏抜け・オフサイドが現実の量へ近づく |
| S4 | 7対7 → 11対11 | 陣形・役割 | 今の検査がすべて緑 |

前の段階で覚えた重みを、次の段階の出発点にする（最初からやり直さない）。

### 9.3 報酬（点数）の作り — 「フィールドの区分け」と「行動ごとの報酬」

1. **ゴール**: 入れたら +1、入れられたら −1（攻めと守りで合計0）
2. **フィールドの区分け（オーナー指定・使う）**: 今の価値の表（21×14マス・`value_table.ts`）を**場所の点数** Φ にする。
   ボールが点数の高いマスへ進めば攻めに＋、守りに−。
   🔑 **「進んだ分だけ」**（いまの点数 − 前の点数）で与える。こうすると**同じ場所を行ったり来たりしても点が貯まらない**
   （行き来すると＋と−が打ち消す）。これは「最適な動きを変えずに学習を速める」点の与え方として知られている形
   （Ng, Harada & Russell 1999「ポテンシャルに基づく報酬整形」）
3. **行動ごとの報酬（オーナー指定・使う）**: 奪った・枠へ撃った・前へのパスが通った、などに小さな点。
   🔴 これは**抜け道を生みやすい**（例: パスの点のために横パスを永遠に回す）。そこで
   - 点は小さく、**段階が進むごとに減らして最後は0**（行動を「覚えるきっかけ」に使い、最終的な動きはゴールと場所の点で決まる）
   - 学習のたびに**行動の回数を相場と並べ**、急に増えた行動は抜け道として止める（9.5）
4. 守る側の点も同じ表から作る（攻める側の点の反対）

### 9.4 正しい結果

- 正しい1: S1 で、学習した攻めが**今のAIの守り**から、学習した守りが**今のAIの攻め**から、どちらも勝ち越す
- 正しい2: 同じ学習した方針でも、**隠しパラメーターと能力で動きが変わる**（裏抜け型は裏を、技術の高い選手は抜きを選ぶ）。
  型の個性の検査（`tests/identity.test.ts`）と同じ考え方で数える
- 正しい3: 攻めと守りを互いに鍛えても（自己対戦）、**どちらかが1つの技だけに落ちない**（抜き方・止め方に複数の型が残る）
- 正しい4: ゲームの中では**同じシード・同じ重みなら同じ試合**（試合を2回回して完全一致）
- 正しい5: 11対11 に着いたとき、出典つきの相場（得点・シュート・決定率・走行・疲れ方・撃つ場所・幅）が緑のまま、
  **今の評価式より自然**とオーナーが目視で判断する

### 9.5 間違った結果（これが出たら止める）

- 間違い1: **報酬の抜け道**。点を貯めるだけの動き（横パスを回し続ける・同じマスを往復・守りがゴールライン上に立ち尽くす・
  奪ってすぐ外へ蹴り出す）。行動の回数・場所が相場から大きく外れたら抜け道とみなす
- 間違い2: **能力を無視した最強の1手**。どの選手も同じ動きになり、特訓の意味が消える（間違い1 と同じくらい重い）
- 間違い3: **学習相手にだけ強い**（自己対戦の相手にしか勝てず、今のAIや別の型に負ける）。評価は決まった相手の組で行う
- 間違い4: ゲームの中で結果が揺れる（重みの読み込み・計算の順番・浮動小数の扱いで、同じシードが違う試合になる）
- 間違い5: 物理の外の動き（速さの上限を超える・ボールを持ったまま瞬間移動）。物理は学習AIからは変えられない作りにする

### 9.6 定量の基準

| 段階 | 指標 | 合格ライン | 測り方 |
|---|---|---|---|
| S1 | 学習した攻め × 今の守り | 得点率が今の攻め × 今の守りより高い | 決まったシードで1,000回 |
| S1 | 学習した守り × 今の攻め | 失点率が今の守りより低い | 同上 |
| S1 | 動きの種類 | 抜き方（向き・速さの組）が2つ以上のまとまりに分かれる | 行動の記録を数える |
| S1 | 能力の効き | 速さ／技術の高い攻めほど得点率が高い（逆にならない） | 能力を変えて同じ回数 |
| 全段階 | 決定論 | 同じシード・同じ重みで2回回して完全一致 | 自動テスト |
| 全段階 | 抜け道 | 行動の回数が前の段階の2倍を超えたら止めて原因を見る | 学習のたびに自動で並べる |
| S4 | 相場 | `npm run check` がすべて緑・型の個性が緑 | 今の検査そのもの |

### 9.8 前提条件

| 前提 | 崩れた場合の影響 | 代替策 |
|---|---|---|
| シミュレーターが十分速い（いま90分の試合が約0.2秒・16コア） | 学習が終わらない | 1対1は試合を短く切る（攻撃1回ごと）。足りなければ学習だけ別の環境へ |
| 1秒刻みで駆け引きが表せる | フェイント・間合いが出ない | S1 で確かめ、出なければ刻みを細かくする（0.25秒など）。**物理の作り直しになるのでオーナー判断** |
| 学習の方法は TypeScript の進化戦略から始める（Python・GPU 不要） | 伸びが止まる | 強化学習（PPOなど）へ切り替え。そのときは費用をオーナーに相談 |
| 計算の決定論（重み×盤面の掛け算・足し算と、`detmath` の関数だけを使う） | 同じシードで揺れる | 活性化は掛け算と比較だけで済むもの（ReLU）にする |
| 今のAI（評価式）は比べる相手として残す | 良くなったか分からない | ブランチ `shot-consistent-value` を先に区切る |
