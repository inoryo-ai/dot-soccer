# 決定事項（要件定義書 §12 の矛盾への決着）

> 出典: `Downloads/ドットサッカー育成ゲーム 要件定義書（ドラフト）.md` §12
> この文書が実装の正本。要件定義書と食い違ったら**こちらが新しい**（要件定義書側も追記で直す）。
> 決定日: 2026-09-30

## D-01 判定1（バランス）の条件に守備側を足す（§12-#1）

**問題**: マンツーマン特訓は `zone_man` しか動かさず `press` は10のまま。
判定1「攻撃系の最大値 < 閾値 かつ press < 閾値」が常に真になり、**永遠にバランス**。
堅守型プリセットも全員バランスになり「20回以内にタイプが1回は変わる」が落ちる。

**決定**: 判定1に `|zone_man| < 閾値` を足す。さらに守備タイプを2つ新設する。

| 追加タイプ | 条件 | 理由 |
|---|---|---|
| マンマーカー | `zone_man >= 25` かつ `press < 50` | マンツーマン特訓の到達先が無かった |
| プレッサー | `press >= 25` かつ `|zone_man| < 25` | プレス特訓の到達先が無かった（ストッパーは press>=50 が必要で20回でも届かない） |

## D-02 ゾーン特訓カードを追加する（§12-#2）

**問題**: `zone_man` を下げるカードが無く、初期値0からマイナスにならない＝スイーパーに到達不能。

**決定**: 7枚目のカード「ゾーン」を追加する。マンツーマンの鏡像。

| カード | 見える能力 | 隠し | もらえる条件（課題） |
|---|---|---|---|
| ゾーン | physical +3 | zone_man **-4** | 被シュートが多い |

スペシャルの組み合わせは 6枚 C(6,2)=15 → **7枚 C(7,2)=21種**になる（§12-#6 で全21種に命名）。
ただし「マンツーマン＋ゾーン」は zone_man が打ち消し合うため、**同時使用を禁止**する（相反カード）。
実装上の有効なスペシャルは **20種**。

## D-03 閾値を 40 → 25 に下げる（§12-#3）

**問題**: 初期値10＋毎回+2だと判定1の閾値40に届くのは15回目。目標「3〜10回」に収まらない。

**決定**: タイプ判定の閾値を **25** にする（上昇量は要件定義書どおり +2 / zone_man は ±4）。

| カード | 到達回数 | 到達タイプ |
|---|---|---|
| ランニング (overlap +2) | 8回 | ダイナモ |
| プレス (press +2) | 8回 | プレッサー |
| パス (support +2) | 8回 | レジスタ |
| ダッシュ (run_space +2) | 8回 | アタッカー |
| シュート (goal_wait +2) | 8回 | ストライカー |
| マンツーマン (zone_man +4) | 7回 | マンマーカー |
| ゾーン (zone_man -4) | 7回 | スイーパー |

7〜8回＝目標「3〜10回」の範囲内、かつテスト「20回以内」も満たす。
閾値は `constants.py` の `TYPE_THRESHOLD` 1箇所。上昇量を触らないので特訓の体感は要件定義書どおり。

## D-04 同値時の優先順を固定する（§12-#4）

**問題**: 「最大」「上位2つ」の判定で、初期値10が4つ並ぶと結果が実装依存になる。

**決定**: 2段構えにする。

1. **攻撃タイプ判定に入る門**: `max(攻撃系4種) >= 25` を満たさない限り、攻撃タイプ（ストライカー／アタッカー／ダイナモ／レジスタ）の判定に入らない。
   → 全部10で並んでいる段階では**同値判定自体が発生しない**。
2. それでも同値が出る場合の順位は**固定リスト**で決める:
   `run_space > goal_wait > overlap > support`
   （この順でないとランニング特訓がダイナモに到達できない＝D-03の表が成立しない）

## D-05 「攻撃系5種」は4種の誤記（§12-#5）

**決定**: 攻撃系は `support, overlap, run_space, goal_wait` の **4種**。`press` は守備側で別扱い。

## D-10 上位2つの組み合わせが表に無い場合は、最も高い1つで決める（実装中に発見）

**問題**: 要件定義書 §7 の8ルールは、攻撃系4種の上位2つの組み合わせ6通りのうち
**2通りしか覆っていない**（{run_space, goal_wait}＝アタッカー、{overlap, run_space}＝ダイナモ）。
残る {overlap, support} {overlap, goal_wait} {run_space, support} {support, goal_wait} は
どのルールにも当たらず「バランス」に落ちる。

スペシャル特訓は攻撃系2つを**同じだけ**上げるため、この穴に落ちるものがある。
実測で **パス＋ランニング / ランニング＋シュート / ダッシュ＋パス / パス＋シュート の4組が、
20回特訓してもタイプが変わらなかった**（テストが検出）。

**決定**: 判定5（レジスタ）の後に「最も高い1つで決める」段を足す。

| 最大の攻撃系 | タイプ |
|---|---|
| goal_wait | ストライカー |
| run_space | アタッカー |
| overlap | ダイナモ |
| support | レジスタ |

＝ペアのルールは「2つが同時に育った形」を捉える表、最後の1段は**取りこぼしを無くす受け皿**。
これで攻撃系が育った選手が「バランス」に留まることは無くなる。

## D-07 タイプは保存せず、隠しパラメーターから毎回導出する

学習台帳「導出できる値を別に持たない」（3回・機械化済み）に従う。
`Player.type` はフィールドではなく**プロパティ**。JSONにも書かない。
`data/*.json` にタイプが書かれていたら検査で落とす（`scripts/check_project.ts` の [3]）。

## D-08 乱数・時刻は引数で受ける

学習台帳「内部で `new Date()` を読む関数は一番間違えやすい瞬間を検査できない」に従う。
`random` のモジュール関数は使わず、`random.Random(seed)` のインスタンスを引数で渡す
（TypeScript 版では `PyRandom`。`Math.random` は使わない）。
バッチの各試合のシードは `seedFor(baseSeed, pairIndex, matchIndex, swapped)` で**決定論的に導出**する
（実行順・並列度が変わっても結果が変わらない）。

## D-09 バッチは並列実行する（性能上の決定）

総当たり 15組 × 200試合 × ホーム/アウェー = **6,000試合**。1試合 5,400ティック × 22人。
単一プロセスでは現実的な時間に収まらないため、コア数分に分割する
（Python 版は `multiprocessing`、TypeScript 版は `worker_threads`。どちらも外部ライブラリ不要）。D-08 によりシードは試合ごとに独立導出されるので、並列でも結果は同一。

## D-15 Python から TypeScript へ書き直す（2026-10-02・オーナー指示）

ブラウザ版は Pyodide（ブラウザで Python を動かす仕組み、約10MB）を毎回読み込んでいた。
TypeScript にすると、規則（`src/sim/`）を**そのまま**ブラウザでも端末でも動かせ、
「規則は1か所にしか書かない」（`web/bridge.js` の 🔴）を保ったまま待ち時間が無くなる。

🔴 **書き直しで一番起きやすいのは「動くし試合も成立するが、中身が少し違う」こと。**
   乱数を引く順番・丸め方（Python の `round` は偶数への丸め）・同点のときの選び方・
   浮動小数の剰余の符号。どれも見ても気づけない。

🔑 だから Python 版（コミット 8b126f0）に正解データを書き出させ（`tools/gen_golden.py`）、
   TypeScript 版が**同じシードで同じ結果**を出すことを1値ずつ照合した
   （`tests/golden.test.ts` `tests/cli.test.ts`）。照合したのは、乱数列・プリセット7チーム・
   特訓・試合26件（イベント1件ずつ）・再生用の座標5,400コマ・一括対戦・2シーズン通しのキャリア・
   コマンドの出力・対話画面を最後まで歩いた全記録。
   乱数は Python の `random.Random`（メルセンヌ・ツイスタ）を写した `src/sim/pyrandom.ts`、
   文字列の種のための SHA-512 も `src/sim/sha512.ts` に自前で持つ（外部ライブラリを足さない）。

## D-16 三角関数・指数関数は四則演算だけで計算する（決定論の強化）

`Math.sin` などの最後のビットは**JS エンジン（ブラウザ）ごとに違う**。Python の `math.sin` も
OS の数学ライブラリ次第で、macOS では cos・sin の約15%が、正しく丸めた値と1ビット違っていた
（2026-10-02 実測・2万件）。試合は1ティックのずれが残り全部に伝わるので、
これでは D-08「同じシードなら同じ試合」が、OS やブラウザをまたぐと守れない
（Python 版も macOS・Linux・Pyodide で結果が変わりうる状態だった）。

🔑 `src/sim/detmath.ts` に sin / cos / atan2 / exp を四則演算と平方根（どの環境でも結果が1つに
   決まる）だけで書いた。手順は fdlibm の考え方に沿い、誤差は最大1.3ビット程度。
   `math.hypot` は CPython 3.11 の手順を `src/sim/pymath.ts` に写した（`Math.hypot` とは
   400件中129件で最後のビットが違った）。
🔴 `tools/detmath.py` に一字一句同じ手順の Python 版があり、正解データはそれを差し込んで作った。
   片方だけ直すと照合できなくなる。
🔴 そのため、TypeScript 版の試合結果は **macOS で動かしていた Python 版とは細部が違う**
   （同じシードでも別の試合になりうる）。勝率表などの数字は TypeScript 版で測り直したものを使う。
   画面の描画（`src/web/pitch.ts`）は結果に戻らないので Math.sin のままでよい。

## D-17 「スタミナが20%未満になった選手」の数え間違いを直す

Python 版は数えた選手を `id(選手)`（メモリ上の番地）で覚えていた。交代で退いた選手が
メモリから消えると、その番地が新しく入った選手に使い回され、**「もう数えた選手」と誤判定**されて
人数が少なく出ていた（走力型 vs プレス型 seed=1000 で 14人のところ 11人）。
スコアや経過には影響しないが、スタッツの表示と「ランニング」カードの判定に関わる。
TypeScript 版は**選手そのもの**を覚える（`Set<Actor>`）。正解データも、この1点だけ直した
Python で作った（`tools/gen_golden.py` の `_track_stamina_by_actor`）。

## D-18 キックオフは自陣から、ゴールの後は全員が戻ってから再開する

2026-10-02 のオーナー指摘:「そもそもスタート時に選手が敵陣地に入ってるし、ゴールしても
一度完全に戻らないといけないのにそのまま始めるし」。どちらも Python 版からあった。

- **キックオフの立ち位置**に、試合中の持ち場をそのまま使っていた。FW の持ち場は自ゴールから
  70% なので、試合開始の時点で相手陣地にいた（バランス型 vs プレス型で 3人と2人）。
  → 自ゴールから 35% より前の持ち場を自陣へ畳み（FW 0.70 → 0.47）、センターラインの約2m手前を
  越えないようにした。守る側はセンターサークル（半径9.15m）の外へ出す。蹴る人だけセンター。
  試合開始・後半開始・ゴール後のすべてに効く。
- **ゴールの後**、全員をその場でキックオフの位置へ瞬間移動させ（1コマで 40m 以上）、
  次の1秒でもう蹴り出していた。画面はコマの間をつなぐので、全員が一斉に滑って戻って見えた。
  → 全員がキックオフの位置へ**歩いて戻り**、そろってから蹴り出す。戻っている間は誰もボールに
  触れず、ボールもセンターへ戻る。最短10秒・最長120秒（実測は 13〜47秒・中央 24秒）。
- **戻っている間も時計は進める**（オーナー判断）。実際のサッカーと同じで、その分プレー時間は減る。

🔴 近づいたら減速する（残りの半分ずつ詰める）。減速しないと、足の速い選手が向きを変えきれずに
   立ち位置の周りを回り続け、180秒待ってもキックオフにならない試合があった。
🔑 戻る道のりは位置だけで決まり、乱数を引かない（D-08 の決定論はそのまま）。
🔴 試合の結果が変わるので、Python 版の正解データのうち試合まわり（matches / batch / career / cli）は
   `scripts/gen_golden.ts` で TypeScript 版から作り直した。この生成スクリプトは、規則を変える前の
   main で回すと Python 版の正解データと**完全に一致する**ことを確かめてから使った。
   乱数・数学・プリセット・特訓（random / math / presets / training）は今も Python 版との照合のまま。
   検査: `tests/kickoff.test.ts`

## D-19 パスの区切り文字を1か所でそろえ、検査を Windows と Linux の両方で機械にかける

2026-10-02、TypeScript 版（D-15）を**初めて Windows の開発機で動かしたところ2件が赤になった。**
どちらも試合の規則とは無関係で、**パスの区切り文字**（Windows は `\`、Mac/Linux は `/`）だけが原因。

- `npm run check` [10] が、配った16ファイル全部を「一覧にあるのに配られていない」と報告した。
  `manifest.json` 側は `/` なのに、照合する側（`scripts/check_project.ts`）が
  `relative()` の戻り値をそのまま使って `\` のままだった。
  🔴 **同じ行の下にある「`cli/` `node/` が混ざっていないか」の検査も、`/` 前提の正規表現なので
  Windows では一度も一致していなかった＝守っているつもりで守っていない状態**だった。これが一番危ない。
- `tests/cli.test.ts` が正解データと1行ずれた（`<SAVE_DIR>\s.json` と `<SAVE_DIR>/s.json`）。

🔑 **直し方**: 一時フォルダ名の置き換えを `tests/helpers.ts` の `maskSaveDir()` 1本にまとめ、
   正解データを**作る側**（`scripts/gen_golden.ts`）と**照合する側**（`tests/cli.test.ts`）が
   同じ関数を使うようにした。別々に書くとまたズレる。
   `check_project.ts` は `build_web.ts` と同じ `.split("\\").join("/")` をかけた
   （`build_web.ts` は元から正規化していた。**漏れていたのは照合側だけ**）。

🔴 **なぜ気づけなかったか＝正本（main）が一度も Windows で動いていなかった。**
   書き直しは Linux 系で作られ、検査もテストもそこでしか回っていない。
   **症状は OS を変えた瞬間にしか出ない種類なので、回す場所を増やす以外に検出手段がない。**
   → `.github/workflows/ci.yml` を追加し、**ubuntu と windows × Node 22.18 と 24** の4通りで
   `typecheck` → `test` → `check` を回す。Node 22.18 は `package.json` の `engines` に
   書いてある下限で、書いてあるだけの約束にしないため実際に動かして確かめる。
   （学習台帳の昇格ルール＝同じ原因が3箇所で出たので機械化する）

## D-20 見た目を「明るい地に濃い輪郭」へ作り直し、操作を画面の下へ固定する

2026-10-02 オーナー指示:「カイロソフトのデザインとアニメーションを参考に、UIと導線も寄せる」。

🔴 **参考にするのは様式まで。** 上から見たピッチ・ドット絵・**コマンドを選んで進める**という
   経営シミュレーションの作法を借りる。特定の作品のロゴ・キャラクター・配色そのもの・
   画面写真は複製しない（§12）。色・寸法・刻み方はこちらで決めた。

変えたこと:

- **暗い画面をやめた**（`--bg #10161c` → `--paper #f6ead0`）。このジャンルは明るい地に
  濃い輪郭で、面を紙のように重ねる。影は**ぼかさず2pxずらすだけ**にした。ぼかすと
  「切って重ねた」感じが消えて、現代のカードUIに戻ってしまう。
- **寸法をすべて `--px`(2px) の倍数にした。** 枠・影・間隔・animationの刻みを揃える。
  中途半端な1pxが混ざると、拡大したときだけ滲んで見える。
- **動きは `steps()` で刻む**（4〜8コマ）。なめらかに動かすと現代のUIになる。
  同じ動きでも刻むとドット絵の側に寄る。
- 🔴 **タブを画面の上から下へ移した（導線）。** もとは上のタブで、親指から遠く、
  「次に押すもの」を上に探させていた。下に固定した大きなコマンドの札4つに変えた。
  絵は CSS が `box-shadow` で**1ピクセルずつ打つ**（外部画像もアイコンフォントも読まない）。
- 🔴 **特訓と試合結果を「画面の前に出す」形にした。** もとは一覧の下にそのまま生えていて、
  選んだのに表示が画面の外にあることがあり、「押したのに何も起きない」に見えた。
  跳ねて出る（行き過ぎてから戻る）＋後ろを暗くして、触る場所を1つに絞る。
- **伸びた能力を数字で飛ばす**（`src/web/fx.ts` を新設）。特訓は「表のどこかの数字が
  41→43 になる」だけの出来事で、**画面を見ていても起きたことに気づけない**。
  🔑 飛ばす数字は `now - before`（実際に動いた差）にした。`r.deltas` は「かけようとした量」で、
  上限に当たると実際はそこまで伸びない。要求量を飛ばすと数字だけ増えて表は変わらない＝嘘になる。
  🔑 粒の飛ぶ向きは等間隔で、**乱数を引かない**。演出で乱数を引くと、同じシードでも見た目が
  変わり、「同じ結果になる」の確認（D-16）が目で追えなくなる。
- **GK に専用の色 `--gk` を作った。** 値は `--danger` と同じだが意味が違うので変数を分ける。
  危険色を直に使うと「GKは危険」という読み方が生まれ、あとで危険色だけ変えたときに
  ユニフォームまで一緒に変わる。この値は `src/web/pitch.ts` の `KIT.gk` と揃える。
- 🔴 **`pitch.ts` の色を `style.css` の `:root` と同じ値に揃えた。** canvas は CSS 変数を
  読めないので二重に書くことになる。片方だけ変えると盤の芝と画面の芝が違う緑になり、
  それだけで安く見える。ずらすのは「盤の中だけで意味がある差」（縞・影）に限る。

🔑 **`src/web/fx.ts` も規則を1行も持たない**（§6 の三層をそのまま守る）。
   渡された文字を渡された場所から飛ばすだけで、何がいくら伸びたかは `src/sim/` が決める。

🔬 **検査を1つ増やした（[10] の中）**: `src/web/*.ts` の `$("...")` が名指しする id が
   `web/index.html` に実在すること。`$()` は無い id を渡されるとその場で例外になるが、
   起きるのは**ブラウザでその画面を開いた瞬間だけ**で、型チェックもテストも全部緑のまま通る。
   導線を変えて骨組みを動かすたびにこの踏み方が待っているので、機械で突き合わせる。
   歯があることは id を1つ壊して赤くなることで確かめた（70個を照合）。

## D-21 `hidden` を必ず効かせる／フルHDでは `--px` ごと拡大する

2026-10-02 オーナー指摘2件。

**①「ゴールの画面が出続けてる」** — `display` の上書きだった。
ブラウザ内蔵の `[hidden] { display: none }` は**属性セレクタ1つぶんの強さしか無い**ので、
`.goal-flash { display: grid }` のような class の指定に負ける。負けると `main.ts` の
`box.hidden = true` が**何もしない**。
🔴 消えないだけでなく、**ページを開いた時点から出たまま**になる（HTML の `hidden` も効かないため）。
🔴 画面は普通に動き、例外も出ず、テストも検査も緑のまま通る。
🔑 1要素ずつ直さない。`hidden` を使う要素は他に5つある
（`#trainPanel` `#matchResult` `#errorBox` `#historyPanel` `#trainResult`）。
`[hidden] { display: none !important }` で**まとめて勝たせた**。`!important` はこの1行だけ。

**②「画面サイズが小さい。フルHDでいい」** — 1920×1080 で本文が 768px の細い帯だった。
🔑 広げ方は2段構え。**`--px` を 2px → 3px にする**と、寸法を全部その倍数で書いてあるので
枠・影・間隔・コマンド帯・コマンドの絵が**まとめて1.5倍**になる。そのうえで本文 1180px、盤 960px。
🔴 **ドット絵は整数倍でしか拡大しない。** 1100px のような幅だと倍率が 2.29倍になり、
1ドットが 2px の列と 3px の列に割れて縞ムラが出る（`image-rendering: pixelated` はムラを消さない）。
だから 960px＝ちょうど2倍で止める。縦が 940px 未満の窓では従来どおり伸縮させる
（2倍にすると操作ボタンが画面の外へ出るため）。

## D-26 背景だけ絵を持ち込む。動くものは手続きのまま（2026-10-03・オーナー判断）

🔴 **要件 §12「画像ファイルを持ち込まない」を、背景に限って変える。**

§12 は出どころの問題を起こさないための規則だった。だが背景を手続きで描くと
**密度に天井がある**。人は長方形7枚、机は箱1つ。参考の絵は「日よけが少し傾いて、
布がたるんで、影が落ちている」。ルールで描ける形には限界があり、
**そこは手を入れた量では埋まらない**（実際、数回手を入れて差が縮まらなかった）。

🔑 **変えたのは背景だけ。** 選手とピッチは手続きのまま。理由は2つ:

1. **着せ替えが壊れる。** 商店街で見た目を買える仕様なので、選手のドット絵は
   実行時に色を差し替えられる必要がある。焼き込むと色の数だけ画像が要る。
2. **状態で描き分けるものは手続きが正しい。** 試合中の向き・走り・ボールは
   毎コマ変わる。これは絵にできない。

| | 手続き | 絵 |
|---|---|---|
| 背景（街・施設の中） | 天井あり | ◎ こちらにする |
| 選手・ピッチ | ◎ **これが正しい** | ✕ 着せ替えが死ぬ |

### 作り

- `web/bg/` に置き、`STATIC_DIRS` が**中身を触らずに**写す。
- 画面と絵の対応は `main.ts` の `BG_PHOTO` 1か所。絵が用意できた画面から1行ずつ移せる。

  （`model.py` だけ古い写しが読まれた 2026-09-30 と同じ踏み方）。
- 🔴 背景が絵になると、**地の上に字を置くだけでは読めない**（「サッカー場」が木と観客に

- 🔴 **権利の確認が未了。** AI生成画像の商用利用の扱いは定まっていない。

## D-27 試合を全画面にして、選手に姿勢を持たせる（2026-10-03）

オーナー指摘「小さすぎて見えない。フルHDで大きく」＋「アニメーションを厚く」。

### 盤を大きくする

- 盤を **480×360 → 640×360（16:9）** に。**3倍がちょうど 1920×1080**。
- 得点板・実況・操作を**盤の上に重ねた**。縦に積むと、積んだぶんだけ盤が小さくなる。
  試合中は上の表示板も出さない（見たいのは得点板であって順位ではない）。
- 倍率は `pitch.ts` の `fit()` が**整数倍だけ**で選ぶ。1.7倍のような端数にすると
  1ドットが 2px の列と 3px の列に割れて縞のムラが出る。
- 🔴 **余白を引かない。** 16px でも引くと、全画面（1080px）で `1064/360 = 2.95` となり
  **3倍に届かず2倍に落ちる**。16px の余白のためにフルHDがフルHDでなくなる。
- 窓にブラウザの枠があると高さが足りず2倍で止まるので、**全画面ボタン**を足した。

### 姿勢（`Act`）

`stand` / `run` / `sprint` / `hold` / `cheer` の5つ。

- **hold**（持っている）: 腕を開いて前へ＝体で隠す形
- **sprint**（全力）: 振り幅を1段大きくし、**上半身を進む向きへ1ドットずらす**。
  足を速く振るだけだと「その場で足踏み」に見える
- **cheer**（喜ぶ）: 両腕を上へ＋2コマで跳ねる。喜びは**腕の形**で伝わる（跳ねるだけでは伝わらない）

🔴 **どの姿勢かを決めるのは `pitch.ts`。`sprites.ts` は渡された姿勢で描くだけ。**
判定を絵の側に持つと、絵のファイルが試合の規則を持つことになる（§6 の三層が崩れる）。
しかも `pitch.ts` が見ているのは**リプレイに入っている数字だけ**で、新しい判定はしない。
🔑 コマ数は増やしていない（増やすと貯める枚数が倍になり、スマホで間に合わなくなる）。

## D-30 スタジアムの周りも3Dで持つ。屋根ではなく外壁で閉じる（2026-10-03・オーナー指示）

**オーナーの言葉**: 「現状はサッカー場だけだけど、背景の観客とかしっかり周りも作った3Dデータが欲しいね」。

選手とピッチを3Dにしてカメラが自由に回るようになった時点で、**背景が2Dだと破綻する**。
カメラを回しても観客席が回らないので、書き割りの前で人形が動いているように見える。
`src/web/stadium3d.ts` に観客席・観客・外壁・広告板・照明塔を置いた。

決めたこと:

- **観客は1人1枚の面**（体＋頭の2枚）しか描かない。箱にすると6倍になる。
  数千人を毎コマ描くので、ここを削らないと動かない。
- **乱数を引かない**（番号から `wob()` で作る）。D-16 の決定論を背景でも守る。
- **屋根を張らない。外壁で閉じる。** 最上段の上に庇を出すと、支柱が無いので
  空中に細い梁が1本走るだけに見え、しかもカメラを上げると観客を隠す。
  見せたいのは観客なので、スタンドの背中を壁で閉じるほうが「競技場」に見える。
- 段は**額縁**として噛み合わせる。南北の箱はその段の外周ぶんだけ横に伸ばす。
  固定幅で伸ばすと内側の段が東西のスタンドを突き抜け、**ピッチの上に灰色の板が乗る**。

### 🔴 この回で直した、描画の土台の間違い2つ

どちらも「絵がおかしい」としか見えず、**実際に画面を見るまで分からなかった**。

1. **大きな面を捨てていた**（`voxel.ts: projectPoly`）
   角が1つでもカメラの後ろに入ると `project()` が null を返す。それを見て面ごと
   捨てていたため、**芝（105×68m）が丸ごと消えて短い白線だけが宙に浮いた**。
   面が大きいほど角はカメラの後ろに回るので、寄るほど地面が消える。
   捨てずに**手前の面で切る**（カメラ座標で、割り算の前に切る）のが正しい。

2. **表裏の判定が逆だった**（`voxel.ts: isFrontFacing`）
   画面の y は**下向き**なので、カメラを向いた面はたすきがけの面積が**負**になる。
   `area <= 0` で捨てていたため、**見える面を捨てて裏側の面を描いていた**。
   箱は輪郭が同じなので、選手やボールでは1年気づけない。観客席で初めて
   「手前の面が消えて空が見える」という形で表に出た。
   判定は `voxel.ts` の1か所にまとめ、`field3d` / `stadium3d` から呼ぶ。

3. **経過時間が負になり得た**（`pitch3d.ts`）
   `requestAnimationFrame` が渡す時刻は「そのコマが始まった時刻」なので、
   `main()` で読んだ `performance.now()` より**前**になることがある。
   1コマ目だけ `dt` が負になり、`frames[-1]` で落ちた。経過時間は負にしない。

🔑 2 は**面の向きを変える表示**（カメラが回る3D）を入れるまで現れない種類の間違い。
   2Dの見下ろし固定では一生出なかった。

## D-31 事務所でサッカー場の盤の上に選手を置く（2026-10-03・オーナー指示）

**オーナーの言葉**: 「サッカー場の画像の上で選手をドラッグ＆ドロップすることで
チームの配置を変更することができるUIが欲しい」。

### 動かせるのは**座標だけ**。枠の順番と位置の名前は動かさない

試合の処理は「`pos === "GK"` の選手がちょうど1人いる」ことを前提に
`find(a => a.pos === "GK")!` で何か所も探している。枠そのものを作り替えられるようにすると、
この前提が壊れて**GKが0人のチームで試合が始まり、その場で落ちる**。

そこで `Tactics.slots` は、**選んだフォーメーションの枠の座標を、同じ順番で上書きするだけ**にした。
位置の名前（GK/DF/MF/FW）も枠の数も `FORMATIONS` のまま動かない。

```
slots: [[x, y] × 11]   // 無ければ（null）フォーメーションの既定どおり
```

- 計算は `effectiveSlots(tactics)` の**1か所だけ**。試合も画面もここを通す。
  2か所に書くと、盤に出ている配置と試合で使う配置がずれる
- 既定のままならセーブに `slots` を書かない（昔のセーブとバイト単位で同じ中身になる）
- **フォーメーションを選び直したら上書きは捨てる。** 枠の数は4つとも11なので検査は
  通ってしまうが、4-4-2 のために置いた座標を 3-4-3 に当てても意味が無い
- GKは自陣 `0.30` まで。盤の上でも**指についてこない**（動かしてから弾くより、
  そもそも越えられないほうが「出せない」ことが手で分かる）

### 試合に効いていることを検査で押さえる

🔴 この手の機能で一番ありがちな壊れ方は「**盤の上では動いているのに、試合では元の位置**」。
遊んでいて気づけないので、`tests/sim.test.ts` に
「配置を変えたら試合の結果が変わる」を置いた。変わらなければ赤になる。

### 拾った不具合

- **`setPointerCapture` は失敗して例外を投げることがある。** 捕まえずに置くと、
  以降の行が実行されず「押しても何も起きない駒」になる。原因は画面からは見えない。
  捕まえられない場合は追従が弱くなるだけなので、`try` で囲って続行する
- **`ValueError` を `GameError` に包み忘れていた**（`api.setLineup`）。包まないと、
  直せる操作ミス（GKを前に出しすぎ）が「想定していない失敗です」と出て不具合に見える
- **盤を画面幅いっぱいにすると縦が 686px になり**、一番外の列（y=0.14 と 0.86）が
  固定ヘッダーと下のコマンド帯の裏に入って**つまめない駒ができる**。幅に上限を置いた

### 指以外でも動かせるようにする

ドラッグ＆ドロップしか無いと、キーボードだけでは配置を変えられない。
駒は `<button>` で、矢印キー（Shiftで大きく）でも動く。

## D-32 試合の節目に演出を置く。キックオフは競技規則に沿わせる（2026-10-03・オーナー指示）

**オーナーの言葉**: 「開始の演出と終了の演出とハーフタイムの演出をそれぞれ作ってほしい。
ボールの先攻後攻はホームアウェイで決めるから、実際のサッカーの開始方法に則って
アニメーションを作成してほしい」。

### 🔑 エンジンはすでに競技規則どおりだった。規則は1行も変えていない

調べたら `Match.run()` はもともと、

- 前半は `resetPositions(0)`（ホームが蹴る）
- `TICKS_PER_HALF` で `direction *= -1`（**エンド交代**）してから `resetPositions(1)`（アウェーが蹴る）

となっていた。つまり「前半と後半は違うチームが蹴り、エンドが入れ替わる」という
競技規則の骨格はすでに入っている。**ゴールデンの作り直しは要らなかった。**

変えたのは、どちらが蹴るかの定義を `kickoffTeamOfHalf(half)` として**関数に出した**ことだけ。
演出がこれを読む。画面側に「前半はホーム」と書き足すと、片方を直したときにもう片方が嘘になる。

本物ではコイントスの勝者が「どちらのゴールを攻めるか」か「キックオフするか」を選ぶが、
このゲームは**ホーム／アウェーで決める**（オーナー判断）。運で決まる要素を増やさないほうが、
同じシードで同じ試合になる筋（D-16）が通る。

### 前半の終わりで**止める**

`pitch.ts` が `TICKS_PER_HALF` のコマで一度止めて `onHalfTime` を呼ぶ。
止めずに通すと、45分の区切りが**数字が変わるだけ**になって気づけない。

🔴 前半の終わりの判定は**試合終了の判定より先**に置く。後ろに置くと、
速さを上げたときに1コマで両方を跨いで**ハーフタイムが飛ぶ**。

### 出さなかったもの

ハーフタイムに出すのは**得点と得点者だけ**。支配率やシュート数は
「前半だけの値」を持っていないので、それらしい数字を作らない。
**無い数字を出すほうが、出さないより悪い。**

### 決めごと

- どの演出も**押せば飛ばせる**。毎試合かならず待たされるのは苦痛
- 「結果まで飛ばす」を押した人には演出も出さない。飛ばしたのに幕が出るのは押した意味の無視
- 幕は**盤を隠しきらない**。真っ黒にすると、選手が並んでいる本物のキックオフの絵が見えない
- 🔴 `curtain()` は `run` が失敗しても**必ず幕を畳む**。畳み忘れると画面の上に透明な板が残り、
  **どこを押しても反応しない**状態になる
- 🔴 **絵文字を笛に使わない。** 笛の絵文字は無く、近いものを置くと**鐘**に見えた。CSSで描く

## D-33 仕切り直し — 試合の描画を3Dに一本化し、パーツ単位で作り込む（2026-10-03・オーナー判断）

**オーナーの言葉**: 「UIとか画面を後回しにしてパーツ類を一つ一つ作りこんでから、
後から再度UI系を開発しなおしたい。現状はゲームシステムとデザインには納得できてるんだけど、
それ以外の部分は作り直したい」。

### 守るもの／作り直すもの

| | 行数 | 扱い |
|---|---|---|
| `src/sim/`（規則） | 4,582 | **触らない。** 255件の検査が守っている |
| デザイン（`scene/stadium.js` と10枚のモック） | — | **触らない** |
| `src/web/`（画面） | 5,163 | パーツ単位で作り直す |
| `src/web/api.ts` | 447 | **据え置き。** 規則との境界で、薄く、専用の検査がある |

### 🔴 2Dドット絵の試合描画を捨てた（`pitch.ts` 698行 + `sprites.ts` 164行）

2Dは `8方向 × 4コマ × 姿勢の数` を手で描く。姿勢を1つ足すたびに**8方向ぶん全部**
描き直すので、動きの数に比例して費用が増えた。だから「蹴る」も「競る」も入らないまま止まっていた。

3Dは**モデル1体・向きは投影が出す・動きは関節を回すだけ**。
**2本持つと同じ直しを2回やることになる**ので、残さず捨てた。

### 外から見える形は変えずに、中身だけ入れ替えた

`pitch.ts` の公開していた形（`attach` / `attachMini` / `fit` / `load` / `state` /
`toggle` / `setSpeed` / `skipToEnd` / `pause` / `resume` / `stop`）は良くできていて、
`main.ts` はそれしか触っていなかった。だから `match3d.ts` を**同じ形で**作り、
読み込み先を差し替えるだけで済んだ。

🔑 **画面の配線（演出・得点板・実況・操作）は作り直していない。** それは捨てる部分ではなく、
UIを組み直すときにも要るもの。壊してよいと言われても、壊さずに済むなら壊さない。

### ついでに消えたもの

- **盤を整数倍で止める指定**（CSS・`fit()`）。ドット絵の縞のムラを避けるための縛りだったが、
  3Dにはドットの格子が無い。**出す場所の実寸そのままで描く**のが一番きれいで、拡大のぼけも出ない
- **`BG_SCENE` の `match`**。3Dが観客席も屋根も自前で描くようになったので、
  後ろにデザインの2Dスタンド帯を敷くと**スタジアムが二重**になった
  （上は2Dの客席、下は3Dの客席、という割れ方をしていた）
- **見比べページ**（`lab.html`）。見比べる相手が無くなったので、
  **選手パーツを単体で確かめる台**に作り変えた

### これからの進め方

**試合まわりのパーツから**、1つずつ「単体で作り込む → 専用ページで目で確かめる」。
UIの組み直しは最後。`docs/decisions.md` の D-19 より前にある `pitch.ts` / `sprites.ts` の
記述は**当時の記録**で、いまの構成ではない。

## D-35 選手AIの設計方針 — 効用の上にガンビットを載せる（2026-10-03・オーナー判断）

**これはまだ実装の決定ではなく、設計の憲章。** 作る順と、作るときに守ることを先に固定する。

### このゲームの売りは「本来触れないサッカーAIを、ユーザーが動かせること」

**オーナーの言葉**: 「このゲームの面白さは本来触る事の難しいサッカーゲームのAIが
自分の自由に動かせるという点にある」「リスクの部分はおそらくこのゲームにおけるキモ」。

🔑 **珍しいのは「選手単位」ではなく「選手単位 × 条件つき」。**
Football Manager にも EA FC にも個人指示はあるが、どれも**常時オンのプリセット**で
「いつ」が無い（ずっと前に出続けるか、ずっと残るかの二択）。
`相手が3人寄せてきたら` のような**状況の切り替え**を選手ごとに書ける商用作品は見当たらない。

### 層は3つ。ガンビットは効用の**上**に載る

```
チームのガンビット（§10・実装済み）  … つまみを動かす（ライン・プレス・裏狙い）
役割のガンビット（未実装・MS-02）    … 意図に倍率をかける／解禁する
個人の判断（効用。未実装）           … 候補を同じ物差しで採点して最大を選ぶ
実行（ステアリング・実装済み）        … 目標へ動く
```

🔴 **順番は入れ替えられない。** いまの個人の判断は**くじ引き**なので、
そこにガンビットの倍率をかけても「当たりやすくなる」止まりで、指示にならない。
**効用化が先、ガンビットが後。** この2つは別の作業ではない。

🔴 **ガンビットは必ず「追加の層」にする。** 下に素のAIを敷き、ルールが1つも
当たらなくても試合が成立すること。FFXII はここで棒立ちになるが、サッカーでは許されない。

### 🔑 条件は列挙しない。**5軸の文法**にする

§10 の固定5条件（`LEADING_LATE` など）では表現できず、かといって50個並べると
覚えられないし組み合わせが検証不能になる。FFXII が `[対象]+[条件]` の2枠で
これを回避しているのと同じ手を使う。

| 軸 | 値 |
|---|---|
| ボール | 自分が持つ／味方が持つ／相手が持つ／こぼれ球 |
| 場所 | 自陣／中盤／敵陣／ペナルティエリア内 |
| 人数 | 寄せている相手が 0／1〜2／3人以上 |
| 試合状況 | リード／同点／ビハインド × 残り時間 |
| 体力 | 十分／残り少ない |

覚えるのは5つ、書けるのは数百通り。**一覧ではなく文法にする。**

#### 🔴 語彙に入れてよいかの判定基準（1つだけ）

> **画面を見て、その条件がいま成立しているかを人が言い当てられるか。**

- 「相手が3人寄せている」→ 数えられる ✅
- 「ペナルティエリア内」→ 線が引いてある ✅
- 「味方の平均スタミナが40%未満」→ **見えない** ❌（表示を足すか語彙から外す）
- 「相手GKの kick が50未満」→ **見えない** ❌（いまの `OPP_GK_WEAK_KICK` がこれ）

言い当てられない条件は、発動してもプレイヤーには**事故にしか見えない**。不快の大半はここから出る。

### 🔴 ガンビットは「上書き」ではなく「解禁」にする

自由に書ける＝**下手に書ける**。素のAIが賢いほどユーザーの介入は改悪になり、
「触らないほうが強い」が最適解になって売りそのものが崩れる。これを避ける道は1つ。

> **素のAIは堅実止まりにする。リスクを取る選択肢は、ルールを書かないと出てこないようにする。**

- 書かない人 → 堅実に戦える（損をしない）
- 書く人 → 上振れも下振れもする（色が出る）

CBの攻撃参加・GKの飛び出し・2トップ同時の裏抜け・失った直後の全員奪回。
これらを**解禁制**にすると、書くことが常に「可能性を増やす」側に働く。

### リスクが成立するための3条件

1. **条件つきで期待値が正であること。** ただ分散が大きいだけの選択肢は、取る理由が無い。
   「ある状況では正しく、別の状況では間違い」でなければ、**いつ取るかを選ぶ意味が生まれない**。
   ここが文法の5軸と直結する。
2. 🔴 **試合側が本当に罰すること。** CBが上がって失ったら、実際に失点が増えなければ
   リスクは**嘘**になる。空間と数的不利が結果に効く作りが要る。
   （既知の宿題「ゴール前で攻撃が止まる」と同じ根。効用化のときに一緒に見る）
3. **支配的なルールを作らないこと。** 1つの正解ルールができると全員が写して色が消える。
   🔑 検査は既にある。`scripts/check_project.ts` [7] が**プリセット同士のじゃんけんの循環**を
   見ているので、同じ検査を**ルール列同士**へ広げればよい。

### 🔑 効いたかどうかは「試合後の集計」で見せる

FFXII のガンビットが機能したのは**発動が即座に目に見える**から（ケアルが飛ぶ）。
サッカーは発動と結果のあいだが10秒空いて、しかも確率なので、同じやり方では調整できない。

```
ルール2「敵陣で寄せが1人以下 → 撃つ」   発動14 / 枠内5 / 得点1 / 奪われた6
ルール4「味方が持ったら裏へ走る」        発動31 / 受けた4 / オフサイド7
```

🔴 **この集計は機能の一部であって、後付けのおまけではない。**
無いとユーザーは勘で書き換えることになり、それ自体が不快の正体になる。

### 追い風になっている既存の作り

- **決定論（D-16）**: 同じシード・同じ相手なら必ず同じ試合。**ルールを1行変えて
  まったく同じ試合を走らせ、差分だけを見られる**。他のサッカーゲームにできない調整手段
- **ゴールデンは巻き添えにならない**: ルールは既にチームのデータの一部
  （`presetPlan` が方針を持っている）。ユーザーが自分のチームに書くルールは
  プリセットの正解データに影響しない＝個人ガンビットを足しても作り直し不要
- **`rigidity`（弾力的↔徹底的）**: ガンビットの効きの強さのつまみとして既にある
- **`intent` の語彙**（RUN_BEHIND / OVERLAP / HOLD_BOX / SUPPORT / KEEP_SHAPE /
  COVER / MARK / HOLD_ZONE）: ガンビットの「行動」欄にそのまま使える
- **`bumpEpoch` / `seen_epoch`**: 「局面が変わったとき」の検出。個人ガンビットの
  判定タイミングに使える（毎ティック判定すると全員の指示が痙攣する）

## D-41 個人の判断を効用にする — ボールを持った人・持っていない人（2026-10-04・オーナー指示）

### 何を変えたか

| | くじの頃 | いま |
|---|---|---|
| 持っている人 | 撃つ気のくじ → 出すくじ（PASS_URGE）→ 運ぶ | 撃つ・味方ごとに出す・運ぶを**同じ物差しで採点して最大**（`onBallChoices`） |
| 持っていない人（攻撃） | 重みつきのくじ（KEEP_SHAPE 35 固定） | 行き先の「受けたら点にどれだけ近いか × 空き × 届くか × 選びやすさ × 体力」の最大（`decideAttack`） |
| 持っていない人（守備） | 重みつきのくじ（HOLD_ZONE 40 固定） | 「放っておいたら相手がどれだけ点に近づくか × 選びやすさ × 体力」の最大（`decideDefend`） |

- 物差しは **そこでボールを持っている価値** `THREAT_PEAK × exp(-THREAT_DECAY × ゴールまでの距離)`（xT の考え方）。
  撃つなら入る確率、出すなら受け手の位置の価値、運ぶなら運んだ先の価値。失えば**相手から見た同じ値**を引く。
- 採点は `src/sim/utility.ts` の `Score` で**項目ごとに理由つき**で残る（Iron Loyalty の Commander の形を借りた。
  コードは C# なので写していない）。試合後の「ルール2が14回発動」（D-35）の集計はこれを数えるだけで出せる。
- 🔴 **最後にくじを引かない。** 同点は先に並んだ候補（＝堅実な側: 撃つ／持ち場を保つ／持ち場を守る）。
  倍率で順位が入れ替われば必ずそちらを選ぶ＝ガンビットが「指示」になる（`tests/utility.test.ts`）。
- 隠しパラメーターは「選びやすさ」の倍率（床 `OFFBALL_TENDENCY_FLOOR`）。**同じ選手でも局面で選ぶものが変わる**
  （`tests/movement.test.ts`）。くじの頃は自陣で持っていても敵陣で持っていても同じ割合だった。
- 判断の途中では乱数を引かない（`tests/ball_decisions.test.ts`）。攻撃時の行き先の「横のばらけ」と
  「見回し始める向き」だけは、選んだ意思に関係なく**毎回必ず2回**引く（引く回数が判断で変わらない）。

## D-42 試合エンジンを作り直す — サイコロをやめ、物理と3層のAIで戦う（2026-10-05・オーナー判断）

**オーナーの言葉**: 「それっぽいサッカーになってるだけで、現状ではそれっぽさから脱却できていません」
「土台のサッカーの部分がシュミレーションとしてしっかりしていなければいけません」
「乱数で決める仕組みは全面排除したい」「階層は３段階に分けて、チームAIから選手AIからステアリングに分ける」。

### なぜ「それっぽい」止まりだったか

いまのエンジンは**判断のあと、結果をサイコロで決めている**。パスは「通る確率」で振って当たれば受け手の足元へ瞬間移動、
シュートは距離の式で振って外れたら必ずゴールキック、奪い合いは 2.2m 以内で毎秒振る。
位置は確率を少し動かすだけで、「届かない」「先に触られる」という物理の決着が無い。
調整は確率の係数（`constants.ts` 424行）で合計を現実に寄せるしかなく、D-41 の「判断を賢くすると物理の甘さが露出する」はこの形。
さらに 1コマ=1秒・判断は5秒に1回なので、**4秒前に決めたことを実行し続ける**（オーナー指摘）。

### 決めたこと

1. **物理は 0.1秒刻み。** 結果（通る・奪う・入る）は全部ここで決まる。
   パス＝転がるボールに誰が先に触れるか、奪取＝足元から離れた瞬間に守備者の足が届くか、シュート＝軌道に GK の手が届くか。
2. 🔴 **結果をサイコロで決める仕組みは全面的にやめる。** 乱数は**まずゼロで作り**、単調すぎたら
   「実行のブレ（蹴ったボールが狙いからズレる。ズレ幅は技術で決まる）」だけを後から足すかを判断する。
   ゼロのあいだは、同じ2チームなら毎回同じ試合になる（違いは能力・作戦・体力からだけ生まれる）。
3. **AI は3層。** その下に AI ではない物理がある。

   | 層 | 決めること | 考え直す頻度 |
   |---|---|---|
   | チームAI | 局面（組み立て／押し込み／プレス／撤退／カウンター）、陣形の高さ・幅・コンパクトさ、役割の割り当て、作戦ルール（D-35 のガンビット） | 1秒ごと＋節目（持ち主が変わった・外へ出た）で即 |
   | 選手AI | 役割の中で何をするか（出す・撃つ・運ぶ・キープ／受ける場所・走り込み・寄せ・マーク）。見えているものだけで判断 | 0.2〜0.3秒ごと |
   | ステアリング | 目標へ体を運ぶ（加速・減速・方向転換・到着・回避）、蹴る・止めるの実行 | 毎コマ |

4. 🔑 **判断の一貫性は「見える特性」と「始めた行動を続ける前提」で作る**（オーナー案）。
   選手を作るときに見える形でパラメーター化し、同じ選手は同じ物差しで選ぶ。
   たたき台: チーム寄り⇔個人寄り／エゴイスト⇔利他的／先読み 深い⇔浅い／反応 早い⇔遅い／粘る⇔切り替えが早い。
   始めた行動は「やり終えた・できなくなった・**はっきり**良い手が出た」まで続ける。この「はっきり」の幅も特性にする。
   🔴 いまの隠しパラメーター（D-07 のタイプ判定に使う）を置き換えるか上に足すかは、軸が固まってから決める。
5. **合っているかは `docs/realism-reference.md` の現実の値で確かめる**（出典つき。StatsBomb 由来は使わない）。
6. **今のエンジンは残し、新しいエンジンは `src/sim/match/` に並べて作る。** 物差しで上回ったら切り替え、
   ゴールデン・テスト・バランスを作り直す（「AIチームも育っている」の赤もそこで扱う）。

### 作る途中で分かったこと（作る順 2〜3）

- 🔑 **候補を絞るのはチームAIの仕事**（オーナー案）。計算の 73% が「持っている人が味方10人×5通りのパスを
  0.2秒ごとに先読み」だった。チームAIが出し先を3人に絞ると 1試合 14.2秒 → 約5秒。
  ⚠️ 速さだけでなく振る舞いも変わる（候補外のフリーの味方は見えない）。特性「チーム寄り⇔個人寄り」で
  個人寄りの選手だけ自分で周りも探す、の形にできる（作る順 5）。
- 🔴 **予測（reach.ts）と実際（体とボール）を同じ物理にそろえないと、パスが崩れる。** チームAIで全員が
  動き出したとたん「味方が先に触る」と読んだパスの 47% が外れた。原因は4つで、どれも直した:
  ① 速いボールがコマの間に足をすり抜けた（判定を「コマの間に通った線」にした）
  ② 反応の間も体は勢いで流れるのに、止まっているとみなしていた
  ③ 出し手に張り付いた相手は反応なしで当たるのに、反応の時間を要求していた
  ④ 走り抜けるとき全速のまま曲がろうとして目標の周りを回り続けた（曲がれる速さまで落とす）
  → 外れは 22.5%（残りは全速で真横へ曲がる場面の見積もりの甘さ・0.5〜1秒）。
- 90分の試走（両チーム同じ能力の 4-4-2）: 成功率 77.5%（現実 78〜81%）、奪取 17回/チーム、
  守備時の陣形 32.9×37.6m。パスは 1,440本/チーム（現実 約470本）だが、まだボールが外へ出ても止まらない
  （実プレー 90分）ので、実プレー1分あたりでは現実の約2倍。平均パス距離 13.0m（現実 19〜21m）は短すぎる。

### 作る途中で分かったこと（作る順 4）

### 作る途中で分かったこと（作る順 5 の前半: シュートと GK・2026-10-05）

オーナー了承のうえで、特性より先に**サッカーとして欠けている動き**（シュート・走り込み・浮き球）を入れることにした。
特性（エゴイスト⇔利他的など）は「何を選ぶか」に効くので、選ぶものがそろってから載せる。

- シュートもサイコロなし: ゴールの幅の5か所×速さ2通りを先読みし、**誰にも触られずにポストの間を越える**と読めたら撃つ。
  触ったときのボールの速さで、止める／はね返る（20 m/s 超・フィールド）／弾く（24 m/s 超・GK）が決まる。
- GK はペナルティエリアの中だけ手と飛び込みのぶん届く。PK の飛び込みの実測（Sci Rep 2022）から、
  手は体の中心から 2.0m、飛び込みで体が 1.5m（2.84 m/s）動く。キャッチしたボールには挑めない（第12条）。
- 🔴 **90分でシュートが1本。** 仕組みの不具合ではなく、**相手ゴールに近づけていない**:
  持っている時間 30分のうち、ゴールまで 30m 以内は 1.2分、20m 以内は 0.1分。
  攻撃側は持ち場のブロックの中でパスを回すだけで、裏へ走る・エリアへ入る動きが無い。
  30m 以内から隅を狙っても 65回中 59回は GK が届く（GK がゴールの 5m 前に立つので遠目は止められる。
  現実もエリア外の決定率は 3.5〜4.2% なので、これ自体はおかしくない）。
