# 決定事項（要件定義書 §12 の矛盾への決着）

> 出典: `Downloads/ドットサッカー育成ゲーム 要件定義書（ドラフト）.md` §12
> この文書が実装の正本。要件定義書と食い違ったら**こちらが新しい**（要件定義書側も追記で直す）。
> 決定日: 2026-09-30

## D-01 判定1（バランス）の条件に守備側を足す（§12-#1）

**問題**: マンツーマン特訓は `zone_man` しか動かさず `press` は10のまま。
判定1「攻撃系の最大値 < 閾値 かつ press < 閾値」が常に真になり、**永遠にバランス**。
堅守型プリセットも全員バランスになり「20回以内にタイプが1回は変わる」が落ちる。

**決定**: 判定1に `|zone_man| < 閾値` を足す。さらに守備タイプを2つ新設する。

| 追加タイプ | 条件 | 理由 |
|---|---|---|
| マンマーカー | `zone_man >= 25` かつ `press < 50` | マンツーマン特訓の到達先が無かった |
| プレッサー | `press >= 25` かつ `|zone_man| < 25` | プレス特訓の到達先が無かった（ストッパーは press>=50 が必要で20回でも届かない） |

## D-02 ゾーン特訓カードを追加する（§12-#2）

**問題**: `zone_man` を下げるカードが無く、初期値0からマイナスにならない＝スイーパーに到達不能。

**決定**: 7枚目のカード「ゾーン」を追加する。マンツーマンの鏡像。

| カード | 見える能力 | 隠し | もらえる条件（課題） |
|---|---|---|---|
| ゾーン | physical +3 | zone_man **-4** | 被シュートが多い |

スペシャルの組み合わせは 6枚 C(6,2)=15 → **7枚 C(7,2)=21種**になる（§12-#6 で全21種に命名）。
ただし「マンツーマン＋ゾーン」は zone_man が打ち消し合うため、**同時使用を禁止**する（相反カード）。
実装上の有効なスペシャルは **20種**。

## D-03 閾値を 40 → 25 に下げる（§12-#3）

**問題**: 初期値10＋毎回+2だと判定1の閾値40に届くのは15回目。目標「3〜10回」に収まらない。

**決定**: タイプ判定の閾値を **25** にする（上昇量は要件定義書どおり +2 / zone_man は ±4）。

| カード | 到達回数 | 到達タイプ |
|---|---|---|
| ランニング (overlap +2) | 8回 | ダイナモ |
| プレス (press +2) | 8回 | プレッサー |
| パス (support +2) | 8回 | レジスタ |
| ダッシュ (run_space +2) | 8回 | アタッカー |
| シュート (goal_wait +2) | 8回 | ストライカー |
| マンツーマン (zone_man +4) | 7回 | マンマーカー |
| ゾーン (zone_man -4) | 7回 | スイーパー |

7〜8回＝目標「3〜10回」の範囲内、かつテスト「20回以内」も満たす。
閾値は `constants.py` の `TYPE_THRESHOLD` 1箇所。上昇量を触らないので特訓の体感は要件定義書どおり。

## D-04 同値時の優先順を固定する（§12-#4）

**問題**: 「最大」「上位2つ」の判定で、初期値10が4つ並ぶと結果が実装依存になる。

**決定**: 2段構えにする。

1. **攻撃タイプ判定に入る門**: `max(攻撃系4種) >= 25` を満たさない限り、攻撃タイプ（ストライカー／アタッカー／ダイナモ／レジスタ）の判定に入らない。
   → 全部10で並んでいる段階では**同値判定自体が発生しない**。
2. それでも同値が出る場合の順位は**固定リスト**で決める:
   `run_space > goal_wait > overlap > support`
   （この順でないとランニング特訓がダイナモに到達できない＝D-03の表が成立しない）

## D-05 「攻撃系5種」は4種の誤記（§12-#5）

**決定**: 攻撃系は `support, overlap, run_space, goal_wait` の **4種**。`press` は守備側で別扱い。

## D-10 上位2つの組み合わせが表に無い場合は、最も高い1つで決める（実装中に発見）

**問題**: 要件定義書 §7 の8ルールは、攻撃系4種の上位2つの組み合わせ6通りのうち
**2通りしか覆っていない**（{run_space, goal_wait}＝アタッカー、{overlap, run_space}＝ダイナモ）。
残る {overlap, support} {overlap, goal_wait} {run_space, support} {support, goal_wait} は
どのルールにも当たらず「バランス」に落ちる。

スペシャル特訓は攻撃系2つを**同じだけ**上げるため、この穴に落ちるものがある。
実測で **パス＋ランニング / ランニング＋シュート / ダッシュ＋パス / パス＋シュート の4組が、
20回特訓してもタイプが変わらなかった**（テストが検出）。

**決定**: 判定5（レジスタ）の後に「最も高い1つで決める」段を足す。

| 最大の攻撃系 | タイプ |
|---|---|
| goal_wait | ストライカー |
| run_space | アタッカー |
| overlap | ダイナモ |
| support | レジスタ |

＝ペアのルールは「2つが同時に育った形」を捉える表、最後の1段は**取りこぼしを無くす受け皿**。
これで攻撃系が育った選手が「バランス」に留まることは無くなる。

## D-07 タイプは保存せず、隠しパラメーターから毎回導出する

学習台帳「導出できる値を別に持たない」（3回・機械化済み）に従う。
`Player.type` はフィールドではなく**プロパティ**。JSONにも書かない。
`data/*.json` にタイプが書かれていたら検査で落とす（`scripts/check_project.ts` の [3]）。

## D-08 乱数・時刻は引数で受ける

学習台帳「内部で `new Date()` を読む関数は一番間違えやすい瞬間を検査できない」に従う。
`random` のモジュール関数は使わず、`random.Random(seed)` のインスタンスを引数で渡す
（TypeScript 版では `PyRandom`。`Math.random` は使わない）。
バッチの各試合のシードは `seedFor(baseSeed, pairIndex, matchIndex, swapped)` で**決定論的に導出**する
（実行順・並列度が変わっても結果が変わらない）。

## D-09 バッチは並列実行する（性能上の決定）

総当たり 15組 × 200試合 × ホーム/アウェー = **6,000試合**。1試合 5,400ティック × 22人。
単一プロセスでは現実的な時間に収まらないため、コア数分に分割する
（Python 版は `multiprocessing`、TypeScript 版は `worker_threads`。どちらも外部ライブラリ不要）。D-08 によりシードは試合ごとに独立導出されるので、並列でも結果は同一。

## D-15 Python から TypeScript へ書き直す（2026-10-02・オーナー指示）

ブラウザ版は Pyodide（ブラウザで Python を動かす仕組み、約10MB）を毎回読み込んでいた。
TypeScript にすると、規則（`src/sim/`）を**そのまま**ブラウザでも端末でも動かせ、
「規則は1か所にしか書かない」（`web/bridge.js` の 🔴）を保ったまま待ち時間が無くなる。

🔴 **書き直しで一番起きやすいのは「動くし試合も成立するが、中身が少し違う」こと。**
   乱数を引く順番・丸め方（Python の `round` は偶数への丸め）・同点のときの選び方・
   浮動小数の剰余の符号。どれも見ても気づけない。

🔑 だから Python 版（コミット 8b126f0）に正解データを書き出させ（`tools/gen_golden.py`）、
   TypeScript 版が**同じシードで同じ結果**を出すことを1値ずつ照合した
   （`tests/golden.test.ts` `tests/cli.test.ts`）。照合したのは、乱数列・プリセット7チーム・
   特訓・試合26件（イベント1件ずつ）・再生用の座標5,400コマ・一括対戦・2シーズン通しのキャリア・
   コマンドの出力・対話画面を最後まで歩いた全記録。
   乱数は Python の `random.Random`（メルセンヌ・ツイスタ）を写した `src/sim/pyrandom.ts`、
   文字列の種のための SHA-512 も `src/sim/sha512.ts` に自前で持つ（外部ライブラリを足さない）。

## D-16 三角関数・指数関数は四則演算だけで計算する（決定論の強化）

`Math.sin` などの最後のビットは**JS エンジン（ブラウザ）ごとに違う**。Python の `math.sin` も
OS の数学ライブラリ次第で、macOS では cos・sin の約15%が、正しく丸めた値と1ビット違っていた
（2026-10-02 実測・2万件）。試合は1ティックのずれが残り全部に伝わるので、
これでは D-08「同じシードなら同じ試合」が、OS やブラウザをまたぐと守れない
（Python 版も macOS・Linux・Pyodide で結果が変わりうる状態だった）。

🔑 `src/sim/detmath.ts` に sin / cos / atan2 / exp を四則演算と平方根（どの環境でも結果が1つに
   決まる）だけで書いた。手順は fdlibm の考え方に沿い、誤差は最大1.3ビット程度。
   `math.hypot` は CPython 3.11 の手順を `src/sim/pymath.ts` に写した（`Math.hypot` とは
   400件中129件で最後のビットが違った）。
🔴 `tools/detmath.py` に一字一句同じ手順の Python 版があり、正解データはそれを差し込んで作った。
   片方だけ直すと照合できなくなる。
🔴 そのため、TypeScript 版の試合結果は **macOS で動かしていた Python 版とは細部が違う**
   （同じシードでも別の試合になりうる）。勝率表などの数字は TypeScript 版で測り直したものを使う。
   画面の描画（`src/web/pitch.ts`）は結果に戻らないので Math.sin のままでよい。

## D-17 「スタミナが20%未満になった選手」の数え間違いを直す

Python 版は数えた選手を `id(選手)`（メモリ上の番地）で覚えていた。交代で退いた選手が
メモリから消えると、その番地が新しく入った選手に使い回され、**「もう数えた選手」と誤判定**されて
人数が少なく出ていた（走力型 vs プレス型 seed=1000 で 14人のところ 11人）。
スコアや経過には影響しないが、スタッツの表示と「ランニング」カードの判定に関わる。
TypeScript 版は**選手そのもの**を覚える（`Set<Actor>`）。正解データも、この1点だけ直した
Python で作った（`tools/gen_golden.py` の `_track_stamina_by_actor`）。

## D-18 キックオフは自陣から、ゴールの後は全員が戻ってから再開する

2026-10-02 のオーナー指摘:「そもそもスタート時に選手が敵陣地に入ってるし、ゴールしても
一度完全に戻らないといけないのにそのまま始めるし」。どちらも Python 版からあった。

- **キックオフの立ち位置**に、試合中の持ち場をそのまま使っていた。FW の持ち場は自ゴールから
  70% なので、試合開始の時点で相手陣地にいた（バランス型 vs プレス型で 3人と2人）。
  → 自ゴールから 35% より前の持ち場を自陣へ畳み（FW 0.70 → 0.47）、センターラインの約2m手前を
  越えないようにした。守る側はセンターサークル（半径9.15m）の外へ出す。蹴る人だけセンター。
  試合開始・後半開始・ゴール後のすべてに効く。
- **ゴールの後**、全員をその場でキックオフの位置へ瞬間移動させ（1コマで 40m 以上）、
  次の1秒でもう蹴り出していた。画面はコマの間をつなぐので、全員が一斉に滑って戻って見えた。
  → 全員がキックオフの位置へ**歩いて戻り**、そろってから蹴り出す。戻っている間は誰もボールに
  触れず、ボールもセンターへ戻る。最短10秒・最長120秒（実測は 13〜47秒・中央 24秒）。
- **戻っている間も時計は進める**（オーナー判断）。実際のサッカーと同じで、その分プレー時間は減る。

🔴 近づいたら減速する（残りの半分ずつ詰める）。減速しないと、足の速い選手が向きを変えきれずに
   立ち位置の周りを回り続け、180秒待ってもキックオフにならない試合があった。
🔑 戻る道のりは位置だけで決まり、乱数を引かない（D-08 の決定論はそのまま）。
🔴 試合の結果が変わるので、Python 版の正解データのうち試合まわり（matches / batch / career / cli）は
   `scripts/gen_golden.ts` で TypeScript 版から作り直した。この生成スクリプトは、規則を変える前の
   main で回すと Python 版の正解データと**完全に一致する**ことを確かめてから使った。
   乱数・数学・プリセット・特訓（random / math / presets / training）は今も Python 版との照合のまま。
   検査: `tests/kickoff.test.ts`

## D-19 パスの区切り文字を1か所でそろえ、検査を Windows と Linux の両方で機械にかける

2026-10-02、TypeScript 版（D-15）を**初めて Windows の開発機で動かしたところ2件が赤になった。**
どちらも試合の規則とは無関係で、**パスの区切り文字**（Windows は `\`、Mac/Linux は `/`）だけが原因。

- `npm run check` [10] が、配った16ファイル全部を「一覧にあるのに配られていない」と報告した。
  `manifest.json` 側は `/` なのに、照合する側（`scripts/check_project.ts`）が
  `relative()` の戻り値をそのまま使って `\` のままだった。
  🔴 **同じ行の下にある「`cli/` `node/` が混ざっていないか」の検査も、`/` 前提の正規表現なので
  Windows では一度も一致していなかった＝守っているつもりで守っていない状態**だった。これが一番危ない。
- `tests/cli.test.ts` が正解データと1行ずれた（`<SAVE_DIR>\s.json` と `<SAVE_DIR>/s.json`）。

🔑 **直し方**: 一時フォルダ名の置き換えを `tests/helpers.ts` の `maskSaveDir()` 1本にまとめ、
   正解データを**作る側**（`scripts/gen_golden.ts`）と**照合する側**（`tests/cli.test.ts`）が
   同じ関数を使うようにした。別々に書くとまたズレる。
   `check_project.ts` は `build_web.ts` と同じ `.split("\\").join("/")` をかけた
   （`build_web.ts` は元から正規化していた。**漏れていたのは照合側だけ**）。

🔴 **なぜ気づけなかったか＝正本（main）が一度も Windows で動いていなかった。**
   書き直しは Linux 系で作られ、検査もテストもそこでしか回っていない。
   **症状は OS を変えた瞬間にしか出ない種類なので、回す場所を増やす以外に検出手段がない。**
   → `.github/workflows/ci.yml` を追加し、**ubuntu と windows × Node 22.18 と 24** の4通りで
   `typecheck` → `test` → `check` を回す。Node 22.18 は `package.json` の `engines` に
   書いてある下限で、書いてあるだけの約束にしないため実際に動かして確かめる。
   （学習台帳の昇格ルール＝同じ原因が3箇所で出たので機械化する）

## D-20 見た目を「明るい地に濃い輪郭」へ作り直し、操作を画面の下へ固定する

2026-10-02 オーナー指示:「カイロソフトのデザインとアニメーションを参考に、UIと導線も寄せる」。

🔴 **参考にするのは様式まで。** 上から見たピッチ・ドット絵・**コマンドを選んで進める**という
   経営シミュレーションの作法を借りる。特定の作品のロゴ・キャラクター・配色そのもの・
   画面写真は複製しない（§12）。色・寸法・刻み方はこちらで決めた。

変えたこと:

- **暗い画面をやめた**（`--bg #10161c` → `--paper #f6ead0`）。このジャンルは明るい地に
  濃い輪郭で、面を紙のように重ねる。影は**ぼかさず2pxずらすだけ**にした。ぼかすと
  「切って重ねた」感じが消えて、現代のカードUIに戻ってしまう。
- **寸法をすべて `--px`(2px) の倍数にした。** 枠・影・間隔・animationの刻みを揃える。
  中途半端な1pxが混ざると、拡大したときだけ滲んで見える。
- **動きは `steps()` で刻む**（4〜8コマ）。なめらかに動かすと現代のUIになる。
  同じ動きでも刻むとドット絵の側に寄る。
- 🔴 **タブを画面の上から下へ移した（導線）。** もとは上のタブで、親指から遠く、
  「次に押すもの」を上に探させていた。下に固定した大きなコマンドの札4つに変えた。
  絵は CSS が `box-shadow` で**1ピクセルずつ打つ**（外部画像もアイコンフォントも読まない）。
- 🔴 **特訓と試合結果を「画面の前に出す」形にした。** もとは一覧の下にそのまま生えていて、
  選んだのに表示が画面の外にあることがあり、「押したのに何も起きない」に見えた。
  跳ねて出る（行き過ぎてから戻る）＋後ろを暗くして、触る場所を1つに絞る。
- **伸びた能力を数字で飛ばす**（`src/web/fx.ts` を新設）。特訓は「表のどこかの数字が
  41→43 になる」だけの出来事で、**画面を見ていても起きたことに気づけない**。
  🔑 飛ばす数字は `now - before`（実際に動いた差）にした。`r.deltas` は「かけようとした量」で、
  上限に当たると実際はそこまで伸びない。要求量を飛ばすと数字だけ増えて表は変わらない＝嘘になる。
  🔑 粒の飛ぶ向きは等間隔で、**乱数を引かない**。演出で乱数を引くと、同じシードでも見た目が
  変わり、「同じ結果になる」の確認（D-16）が目で追えなくなる。
- **GK に専用の色 `--gk` を作った。** 値は `--danger` と同じだが意味が違うので変数を分ける。
  危険色を直に使うと「GKは危険」という読み方が生まれ、あとで危険色だけ変えたときに
  ユニフォームまで一緒に変わる。この値は `src/web/pitch.ts` の `KIT.gk` と揃える。
- 🔴 **`pitch.ts` の色を `style.css` の `:root` と同じ値に揃えた。** canvas は CSS 変数を
  読めないので二重に書くことになる。片方だけ変えると盤の芝と画面の芝が違う緑になり、
  それだけで安く見える。ずらすのは「盤の中だけで意味がある差」（縞・影）に限る。

🔑 **`src/web/fx.ts` も規則を1行も持たない**（§6 の三層をそのまま守る）。
   渡された文字を渡された場所から飛ばすだけで、何がいくら伸びたかは `src/sim/` が決める。

🔬 **検査を1つ増やした（[10] の中）**: `src/web/*.ts` の `$("...")` が名指しする id が
   `web/index.html` に実在すること。`$()` は無い id を渡されるとその場で例外になるが、
   起きるのは**ブラウザでその画面を開いた瞬間だけ**で、型チェックもテストも全部緑のまま通る。
   導線を変えて骨組みを動かすたびにこの踏み方が待っているので、機械で突き合わせる。
   歯があることは id を1つ壊して赤くなることで確かめた（70個を照合）。

## D-21 `hidden` を必ず効かせる／フルHDでは `--px` ごと拡大する

2026-10-02 オーナー指摘2件。

**①「ゴールの画面が出続けてる」** — `display` の上書きだった。
ブラウザ内蔵の `[hidden] { display: none }` は**属性セレクタ1つぶんの強さしか無い**ので、
`.goal-flash { display: grid }` のような class の指定に負ける。負けると `main.ts` の
`box.hidden = true` が**何もしない**。
🔴 消えないだけでなく、**ページを開いた時点から出たまま**になる（HTML の `hidden` も効かないため）。
🔴 画面は普通に動き、例外も出ず、テストも検査も緑のまま通る。
🔑 1要素ずつ直さない。`hidden` を使う要素は他に5つある
（`#trainPanel` `#matchResult` `#errorBox` `#historyPanel` `#trainResult`）。
`[hidden] { display: none !important }` で**まとめて勝たせた**。`!important` はこの1行だけ。

**②「画面サイズが小さい。フルHDでいい」** — 1920×1080 で本文が 768px の細い帯だった。
🔑 広げ方は2段構え。**`--px` を 2px → 3px にする**と、寸法を全部その倍数で書いてあるので
枠・影・間隔・コマンド帯・コマンドの絵が**まとめて1.5倍**になる。そのうえで本文 1180px、盤 960px。
🔴 **ドット絵は整数倍でしか拡大しない。** 1100px のような幅だと倍率が 2.29倍になり、
1ドットが 2px の列と 3px の列に割れて縞ムラが出る（`image-rendering: pixelated` はムラを消さない）。
だから 960px＝ちょうど2倍で止める。縦が 940px 未満の窓では従来どおり伸縮させる
（2倍にすると操作ボタンが画面の外へ出るため）。

## D-23 街をアイソメ（クォータービュー）で描き直し、UI の主役を青にする

2026-10-02 オーナー指摘（ラフ画像つき）:「奥行きもないし、見た目があんまり面白くない」。

🔴 **正面向きをやめた理由。** 正面から描くと、建物は**前面1枚の板**にしかならない。
屋根も側面も見えないので、どれだけ描き込んでも書き割りのままで、
街の中に場所があるようには見えない。斜め上から見ると屋根・右面・左面の3枚が
同時に見えるので、箱が箱に見える。

- **投影は 32×16 の菱形（2:1）に固定**（`src/web/iso.ts`）。2:1 だと斜めの辺が
  「右へ2・下へ1」のきれいな階段になる。3:2 や 1:1 にすると辺がガタつく。
- 🔴 **奥から手前へ描く**（`gx + gy` の小さい順）。施設も賑やかしも木も**同じ1本の列**に
  入れて並べ替える。別々に描くと、木が建物の前に出たり後ろに回ったりして奥行きが壊れる。
- 🔑 **3面に必ず明るさの差を付ける。** 同じ色だと、どれだけ高くしても平たい六角形に見える。
  上＝明るい／右＝中／左＝暗い、で光の向きを固定する（面ごとに変えると立体が崩れる）。
- 🔴 **画面より大きく地面を敷いて、はみ出しを切り取る。** 最初は画面に収まる広さで敷いたが、
  菱形の地面が**空に浮かぶ島**にしか見えなかった。街は「どこまでも続いている場所の一部」に
  見えないと街に見えない。原点を画面の上へ外し（oy=-160）、四隅まで届く広さ（44マス）にした。
- 🔑 街の絵は **640×360**。**3倍がちょうど 1920×1080** で、フルHDに整数倍のまま収まる。
- **UI の主役を青にした。** それまで枠も見出しも濃茶1色で、情報の階層が「太さ」でしか
  出せていなかった。見出しを青の帯にすると、どこからどこまでが1つの塊かが**色で**読める。
  帯は上を明るく下を暗くする2段（平らな青はシールに見える）。角も丸めた（`--px` の2倍まで）。

🔬 目視でさらに4件直した: 札の折り返し（「選手・戦術・順位／表」と割れていた）／
観客席の市松模様（2色を半々で散らすと屋根に見えた）／席の鮮やかな青が
**プールの水**に見えた（空や川の青と役割がぶつかる）／地図が上に寄って下が空いていた。

### 🔬 測定器の故障: PowerShell の `Select-Object -First` が終了コードを壊す

`npm run build:web | Select-Object -First 3` は **exit 255（実体は -1）** を返す。
`-First` が上流のネイティブコマンドを途中で打ち切るため。**ビルドは成功している。**
同じコマンドを `| Out-Null` で全部読むと exit 0。

🔴 これを3回「原因不明のビルド失敗」として報告しかけた。**出力を途中で切る書き方で
終了コードを判定しない。** 絞り込みたいときは `| Out-String` で全部受けてから
`Select-String` でふるう。
