# 決定事項（要件定義書 §12 の矛盾への決着）

> 出典: `Downloads/ドットサッカー育成ゲーム 要件定義書（ドラフト）.md` §12
> この文書が実装の正本。要件定義書と食い違ったら**こちらが新しい**（要件定義書側も追記で直す）。
> 決定日: 2026-09-30

## D-01 判定1（バランス）の条件に守備側を足す（§12-#1）

**問題**: マンツーマン特訓は `zone_man` しか動かさず `press` は10のまま。
判定1「攻撃系の最大値 < 閾値 かつ press < 閾値」が常に真になり、**永遠にバランス**。
堅守型プリセットも全員バランスになり「20回以内にタイプが1回は変わる」が落ちる。

**決定**: 判定1に `|zone_man| < 閾値` を足す。さらに守備タイプを2つ新設する。

| 追加タイプ | 条件 | 理由 |
|---|---|---|
| マンマーカー | `zone_man >= 25` かつ `press < 50` | マンツーマン特訓の到達先が無かった |
| プレッサー | `press >= 25` かつ `|zone_man| < 25` | プレス特訓の到達先が無かった（ストッパーは press>=50 が必要で20回でも届かない） |

## D-02 ゾーン特訓カードを追加する（§12-#2）

**問題**: `zone_man` を下げるカードが無く、初期値0からマイナスにならない＝スイーパーに到達不能。

**決定**: 7枚目のカード「ゾーン」を追加する。マンツーマンの鏡像。

| カード | 見える能力 | 隠し | もらえる条件（課題） |
|---|---|---|---|
| ゾーン | physical +3 | zone_man **-4** | 被シュートが多い |

スペシャルの組み合わせは 6枚 C(6,2)=15 → **7枚 C(7,2)=21種**になる（§12-#6 で全21種に命名）。
ただし「マンツーマン＋ゾーン」は zone_man が打ち消し合うため、**同時使用を禁止**する（相反カード）。
実装上の有効なスペシャルは **20種**。

## D-03 閾値を 40 → 25 に下げる（§12-#3）

**問題**: 初期値10＋毎回+2だと判定1の閾値40に届くのは15回目。目標「3〜10回」に収まらない。

**決定**: タイプ判定の閾値を **25** にする（上昇量は要件定義書どおり +2 / zone_man は ±4）。

| カード | 到達回数 | 到達タイプ |
|---|---|---|
| ランニング (overlap +2) | 8回 | ダイナモ |
| プレス (press +2) | 8回 | プレッサー |
| パス (support +2) | 8回 | レジスタ |
| ダッシュ (run_space +2) | 8回 | アタッカー |
| シュート (goal_wait +2) | 8回 | ストライカー |
| マンツーマン (zone_man +4) | 7回 | マンマーカー |
| ゾーン (zone_man -4) | 7回 | スイーパー |

7〜8回＝目標「3〜10回」の範囲内、かつテスト「20回以内」も満たす。
閾値は `constants.py` の `TYPE_THRESHOLD` 1箇所。上昇量を触らないので特訓の体感は要件定義書どおり。

## D-04 同値時の優先順を固定する（§12-#4）

**問題**: 「最大」「上位2つ」の判定で、初期値10が4つ並ぶと結果が実装依存になる。

**決定**: 2段構えにする。

1. **攻撃タイプ判定に入る門**: `max(攻撃系4種) >= 25` を満たさない限り、攻撃タイプ（ストライカー／アタッカー／ダイナモ／レジスタ）の判定に入らない。
   → 全部10で並んでいる段階では**同値判定自体が発生しない**。
2. それでも同値が出る場合の順位は**固定リスト**で決める:
   `run_space > goal_wait > overlap > support`
   （この順でないとランニング特訓がダイナモに到達できない＝D-03の表が成立しない）

## D-05 「攻撃系5種」は4種の誤記（§12-#5）

**決定**: 攻撃系は `support, overlap, run_space, goal_wait` の **4種**。`press` は守備側で別扱い。

## D-10 上位2つの組み合わせが表に無い場合は、最も高い1つで決める（実装中に発見）

**問題**: 要件定義書 §7 の8ルールは、攻撃系4種の上位2つの組み合わせ6通りのうち
**2通りしか覆っていない**（{run_space, goal_wait}＝アタッカー、{overlap, run_space}＝ダイナモ）。
残る {overlap, support} {overlap, goal_wait} {run_space, support} {support, goal_wait} は
どのルールにも当たらず「バランス」に落ちる。

スペシャル特訓は攻撃系2つを**同じだけ**上げるため、この穴に落ちるものがある。
実測で **パス＋ランニング / ランニング＋シュート / ダッシュ＋パス / パス＋シュート の4組が、
20回特訓してもタイプが変わらなかった**（テストが検出）。

**決定**: 判定5（レジスタ）の後に「最も高い1つで決める」段を足す。

| 最大の攻撃系 | タイプ |
|---|---|
| goal_wait | ストライカー |
| run_space | アタッカー |
| overlap | ダイナモ |
| support | レジスタ |

＝ペアのルールは「2つが同時に育った形」を捉える表、最後の1段は**取りこぼしを無くす受け皿**。
これで攻撃系が育った選手が「バランス」に留まることは無くなる。

## D-07 タイプは保存せず、隠しパラメーターから毎回導出する

学習台帳「導出できる値を別に持たない」（3回・機械化済み）に従う。
`Player.type` はフィールドではなく**プロパティ**。JSONにも書かない。
`data/*.json` にタイプが書かれていたら検査で落とす（`scripts/check_project.ts` の [3]）。

## D-08 乱数・時刻は引数で受ける

学習台帳「内部で `new Date()` を読む関数は一番間違えやすい瞬間を検査できない」に従う。
`random` のモジュール関数は使わず、`random.Random(seed)` のインスタンスを引数で渡す
（TypeScript 版では `PyRandom`。`Math.random` は使わない）。
バッチの各試合のシードは `seedFor(baseSeed, pairIndex, matchIndex, swapped)` で**決定論的に導出**する
（実行順・並列度が変わっても結果が変わらない）。

## D-09 バッチは並列実行する（性能上の決定）

総当たり 15組 × 200試合 × ホーム/アウェー = **6,000試合**。1試合 5,400ティック × 22人。
単一プロセスでは現実的な時間に収まらないため、コア数分に分割する
（Python 版は `multiprocessing`、TypeScript 版は `worker_threads`。どちらも外部ライブラリ不要）。D-08 によりシードは試合ごとに独立導出されるので、並列でも結果は同一。

## D-15 Python から TypeScript へ書き直す（2026-10-02・オーナー指示）

ブラウザ版は Pyodide（ブラウザで Python を動かす仕組み、約10MB）を毎回読み込んでいた。
TypeScript にすると、規則（`src/sim/`）を**そのまま**ブラウザでも端末でも動かせ、
「規則は1か所にしか書かない」（`web/bridge.js` の 🔴）を保ったまま待ち時間が無くなる。

🔴 **書き直しで一番起きやすいのは「動くし試合も成立するが、中身が少し違う」こと。**
   乱数を引く順番・丸め方（Python の `round` は偶数への丸め）・同点のときの選び方・
   浮動小数の剰余の符号。どれも見ても気づけない。

🔑 だから Python 版（コミット 8b126f0）に正解データを書き出させ（`tools/gen_golden.py`）、
   TypeScript 版が**同じシードで同じ結果**を出すことを1値ずつ照合した
   （`tests/golden.test.ts` `tests/cli.test.ts`）。照合したのは、乱数列・プリセット7チーム・
   特訓・試合26件（イベント1件ずつ）・再生用の座標5,400コマ・一括対戦・2シーズン通しのキャリア・
   コマンドの出力・対話画面を最後まで歩いた全記録。
   乱数は Python の `random.Random`（メルセンヌ・ツイスタ）を写した `src/sim/pyrandom.ts`、
   文字列の種のための SHA-512 も `src/sim/sha512.ts` に自前で持つ（外部ライブラリを足さない）。

## D-16 三角関数・指数関数は四則演算だけで計算する（決定論の強化）

`Math.sin` などの最後のビットは**JS エンジン（ブラウザ）ごとに違う**。Python の `math.sin` も
OS の数学ライブラリ次第で、macOS では cos・sin の約15%が、正しく丸めた値と1ビット違っていた
（2026-10-02 実測・2万件）。試合は1ティックのずれが残り全部に伝わるので、
これでは D-08「同じシードなら同じ試合」が、OS やブラウザをまたぐと守れない
（Python 版も macOS・Linux・Pyodide で結果が変わりうる状態だった）。

🔑 `src/sim/detmath.ts` に sin / cos / atan2 / exp を四則演算と平方根（どの環境でも結果が1つに
   決まる）だけで書いた。手順は fdlibm の考え方に沿い、誤差は最大1.3ビット程度。
   `math.hypot` は CPython 3.11 の手順を `src/sim/pymath.ts` に写した（`Math.hypot` とは
   400件中129件で最後のビットが違った）。
🔴 `tools/detmath.py` に一字一句同じ手順の Python 版があり、正解データはそれを差し込んで作った。
   片方だけ直すと照合できなくなる。
🔴 そのため、TypeScript 版の試合結果は **macOS で動かしていた Python 版とは細部が違う**
   （同じシードでも別の試合になりうる）。勝率表などの数字は TypeScript 版で測り直したものを使う。
   画面の描画（`src/web/pitch.ts`）は結果に戻らないので Math.sin のままでよい。

## D-17 「スタミナが20%未満になった選手」の数え間違いを直す

Python 版は数えた選手を `id(選手)`（メモリ上の番地）で覚えていた。交代で退いた選手が
メモリから消えると、その番地が新しく入った選手に使い回され、**「もう数えた選手」と誤判定**されて
人数が少なく出ていた（走力型 vs プレス型 seed=1000 で 14人のところ 11人）。
スコアや経過には影響しないが、スタッツの表示と「ランニング」カードの判定に関わる。
TypeScript 版は**選手そのもの**を覚える（`Set<Actor>`）。正解データも、この1点だけ直した
Python で作った（`tools/gen_golden.py` の `_track_stamina_by_actor`）。
