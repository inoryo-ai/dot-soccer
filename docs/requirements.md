## 1. 概要と狙い

カルチョビットのようなドットサッカー育成ゲームを、非同期PvPとしてアップグレードし、
NFTと賭け要素を組み合わせる。現在は構想段階（MVPのコマンド版のみ実装済み）。

| 項目 | 内容 |
| --- | --- |
| ジャンル | ドット絵のサッカー育成・非同期PvP |
| 参考作品 | カルチョビット（育成）、FFゾディアックエイジのガンビット（指示）、Steamの売買システム（取引） |
| 事業上の狙い | NFTゲームの成功例を新しい形で実現する |
| NFTの価値の源泉 | 背景やビジュアルの良さ（性能ではない） |
| ステータス | 構想段階。MVP（コマンド版）は遊べる |

## 2. ゲームデザイン方針

勝敗は「緻密な作戦」と「それに合った育成」の噛み合わせで決まる。課金や時間だけでは勝てない構造にする。

| 要件ID | 要件 |
| --- | --- |
| GD-01 | Pay to Winにしない |
| GD-02 | 時間をかけるだけでは勝てない構造にする |
| GD-03 | 強さはパラメーター重視ではなく、価値は見た目（アクセサリー等）を中心に置く |
| GD-04 | アイテムによるパラメーター補正は1/50程度に抑える |
| GD-05 | 作戦と育成が噛み合って初めてチームが成り立つバランスにする |

## 3. 試合システム要件

試合は非同期PvPとし、選手は事前に設定した条件で自動的に動く。ユーザーの操作技術が勝敗に介入する余地は減らす。

| 要件ID | 要件 |
| --- | --- |
| MS-01 | 対戦形式は非同期PvPとする |
| MS-02 | 選手の行動は、FFゾディアックエイジのガンビットのような条件設定で制御する |
| MS-03 | ユーザーの操作技術の介入を減らす |

## 4. 経済圏・賭け要素の要件

賭け要素は収益目的ではなく、ユーザーの熱気を高めるためのものとする。対象はゲーム内通貨のみ。

| 要件ID | 要件 |
| --- | --- |
| EC-01 | 賭けの対象はゲーム内通貨のみに限定する |
| EC-02 | 賭け要素は完全閉鎖の経済圏とする |
| EC-03 | 賭け要素の目的はユーザーの熱気を高めることとし、収益源にはしない |

🔴 **弁護士の確認が済むまで実装しない**（§12）。

## 5. NFT要件

アクセサリーを付帯したキャラクターをNFT化し、外部取引を可能にする。賭けとは経路を分けつつ、導線は繋げる。

| 要件ID | 要件 |
| --- | --- |
| NF-01 | アクセサリーを付帯したキャラクターをNFT化する |
| NF-02 | NFTは外部取引可能にする（イメージはSteamの売買システム） |
| NF-03 | 大会優勝キャラなどの特別キャラクターをNFT化し、自分のチームに入れられる個人的な価値を作る |
| NF-04 | 賭けとキャラクターNFTは経路を分けつつ、導線は繋げる |

🔴 **弁護士の確認が済むまで実装しない**（§12）。

## 6. MVP：試合シミュレーター

最初の成果物は、画面なしでコマンドから動く試合シミュレーターとする。ゲームの核となる次の2点を数字で検証する。

1. 特訓の違いで選手の隠しパラメーターとタイプが変わり、試合中の動きが変わること
2. 大量の自動対戦で勝ちすぎるチームがなく、戦術の相性（じゃんけん関係）が生まれること

| 項目 | 要件 |
| --- | --- |
| 言語 | TypeScript（Node.js 22.18 以上で `.ts` をそのまま実行）。**実行時に外部ライブラリを使わない**（2026-10-02 に Python 3.11 から移行・D-15） |
| 開発ツール | `typescript`（型チェックとブラウザ用の JS 作成）だけ。実行時の制約とは別 |
| 再現性 | 乱数はすべてシード固定。同じシードなら**どの OS・どのブラウザでも**必ず同じ結果（D-16） |
| フォルダ構成 | `src/sim/`（本体）、`src/cli/`・`src/node/`（端末用）、`src/web/`（画面）、`data/`（チームJSON）、`tests/`、`scripts/`、`README.md` |
| 試合規格 | 11対11、ピッチ105×68、1ティック＝1秒、90分＝5400ティック |

決定論的な設計は、本番の非同期PvPでもサーバー権威の試合処理・リプレイ保存・不正検証の土台になる。

## 7. 選手データとタイプ判定

選手は見える能力5種と隠しパラメーター6種を持ち、タイプは隠しパラメーターから自動で決まる。

| 区分 | 項目 | 範囲 | 初期値 |
| --- | --- | --- | --- |
| 位置 | GK / DF / MF / FW | — | — |
| 見える能力 | kick, speed, stamina, technique, physical | 0〜100 | チームごと |
| 隠し | zone_man（負＝ゾーン、正＝マンツーマン） | -100〜100 | 0 |
| 隠し | press, support, overlap, run_space, goal_wait | 0〜100 | 10 |
| 試合中 | 現在スタミナ | 試合中に減る | 最大 |

🔴 **タイプは保存しない。隠しパラメーターから毎回導出する**（D-07）。
保存すると「隠しを動かしたのにタイプが古いまま」という故障の形が生まれる。

### 生まれ持った性質（D-11・2026-10-01 追加）

隠しパラメーター6種が「**何をするか**」を決めるのに対し、こちらは
「**どこまで出るか・どこまで見えるか**」を決める。

| 項目 | 範囲 | 効き方 |
| --- | --- | --- |
| cover_range（カバー範囲） | 15〜90 → 持ち場から 9〜38m | この外へは出ない。広い選手ほど、守っている間も大きく位置を直す。マークで付いていける距離もここから出す（上限22m） |
| vision_range（視野範囲） | 15〜90 → 22〜80m | **見えていないものには反応しない。** 視野が狭い選手は逆サイドのボールに反応しない |

🔴 **特訓では動かない。** オーナー判断（2026-10-01）で、伸ばせる値ではなく
**選手固有の個性**にした。誰を使うかが選択になり、カードは7枚のまま、
スペシャル21通りの命名も動かない。タイプ判定にも関与しない
（`TRAIT_KEYS` は `HIDDEN_KEYS` に入れない）。

🔑 ポジションごとの寄り（DFは持ち場を空けにくい・MFは走り回る）は付けるが、
   個人の振れのほうを大きくして「その枠らしくない選手」も生まれるようにする。

### タイプ判定（D-01〜D-05・D-10 反映後）

閾値は **25**（D-03）。`src/sim/constants.ts` の `TYPE_THRESHOLD` の1か所だけ。
攻撃系は `support, overlap, run_space, goal_wait` の **4種**（D-05。`press` は守備側で別扱い）。

実装は `src/sim/model.ts` の `judgeType`。**上から順に判定し、最初に当てはまったものを返す。**

**0. 何も伸びていない**

- 攻撃系4種の最大 < 25 かつ `press` < 25 かつ `|zone_man|` < 25 → **バランス**（D-01）

**1. 攻撃タイプ**（`max(攻撃系4種) >= 25` のときだけ入る門・D-04）

| # | 条件 | タイプ |
| --- | --- | --- |
| 1-1 | `goal_wait` が最大で、2番目より **15**（`STRIKER_MARGIN`）以上高い | ストライカー |
| 1-2 | 上位2つが `run_space` と `goal_wait` | アタッカー |
| 1-3 | 上位2つが `overlap` と `run_space` | ダイナモ |
| 1-4 | `support` が最大 | レジスタ |
| 1-5 | 上記のどれでもない（上位2つの組み合わせが表に無い） | **最も高い1つ**で決める（D-10） |

🔴 **この門に入ったら守備タイプへは落ちない。** 攻撃側が25以上まで育っていれば、
`zone_man` や `press` がいくら高くても攻撃タイプになる。

🔴 1-5 が無いと、`{overlap, support}` `{overlap, goal_wait}` `{run_space, support}`
`{support, goal_wait}` の4組が表の穴に落ちて**永久にバランスのまま**になる
（スペシャル特訓は攻撃系2つを同じだけ上げるので実際に踏んだ）。

**2. 守備タイプ**（攻撃系が25未満のとき）

| # | 条件 | タイプ |
| --- | --- | --- |
| 2-1 | `zone_man` >= 25 かつ `press` >= **50**（`STOPPER_PRESS`） | ストッパー |
| 2-2 | `zone_man` >= 25 | マンマーカー（D-01 で新設） |
| 2-3 | `zone_man` <= -25 かつ `press` < 50 | スイーパー（D-02 のゾーンカードで到達可能になった） |
| 2-4 | `press` >= 25 | プレッサー（D-01 で新設） |
| 2-5 | どれにも当てはまらない | バランス |

**同値の扱い**（D-04）

- 攻撃タイプの判定に入るのは `max(攻撃系4種) >= 25` のときだけ。
  全部10で並んでいる段階では**同値判定自体が起きない**。
- それでも並ぶときの順位は固定: `run_space > goal_wait > overlap > support`
  （`ATTACK_TIE_BREAK`。この順でないとランニング特訓がダイナモに到達できない）

## 8. 特訓カードと課題の発見

試合で見つかった弱点が課題になり、課題に対応する特訓カードをもらえる。特訓は見える能力と隠しパラメーターを同時に動かす。

| カード | 見える能力 | 隠しパラメーター | もらえる条件（課題） |
| --- | --- | --- | --- |
| ランニング | stamina +3 | overlap +2 | スタミナが20%未満になった選手がいた |
| マンツーマン | physical +3 | zone_man +4 | 奪い合いの負けが多い |
| プレス | speed +3 | press +2 | ボール奪取が少ない |
| パス | technique +3 | support +2 | パス成功率が低い |
| ダッシュ | speed +3 | run_space +2 | 裏を取られた・スピード負けが多い |
| シュート | kick +3 | goal_wait +2 | シュート決定率が低い |
| **ゾーン**（D-02 で追加） | physical +3 | zone_man **-4** | 被シュートが多い |

- 2枚同時使用で「スペシャル」になり、両方の効果が1.5倍（小数切り捨て）
- 🔴 **マンツーマン＋ゾーンは同時に使えない**（D-02）。`zone_man` が打ち消し合うため。
  7枚の組み合わせ21種のうち、有効なスペシャルは **20種**（全20種に名前がある・D-06）
- 能力と隠しパラメーターの上限は100
- 同じ特訓を **3〜10回**続けるとタイプが変わる（D-03 の実測は7〜8回）
- 課題は1試合で同じもの1回まで、最大8枚
- 「多い・少ない」の基準値は `src/sim/constants.ts` にまとめる

## 9. 試合エンジン

各選手は毎ティック、「フォーメーションの基本位置＋チーム戦術＋隠しパラメーター補正」で決まる目標位置へ動く。
隠しパラメーターが動きの違いとして表に出ることがこのゲームの核。

| 局面 | パラメーター | 動き |
| --- | --- | --- |
| 味方保持 | overlap | 高いほど前へ上がる |
| 味方保持 | run_space | 相手DFラインの裏のスペースへ走る |
| 味方保持 | goal_wait | ゴール前に残る |
| 味方保持 | support | ボール保持者に近づく |
| 相手保持 | zone_man | マイナスは自分のゾーンを守る、プラスは近くの相手をマーク |
| 相手保持 | press | 高いほど遠くからボール保持者に寄せる |

| 判定 | 使う能力・要素 |
| --- | --- |
| シュート | 距離と kick。GKの能力と勝負 |
| パス | technique、距離、近くの相手の数。前方で空いている味方を優先 |
| ドリブル | speed と technique。相手の physical と勝負 |
| 奪い合い | 守備側が近くにいると technique＋physical で勝負 |
| スタミナ | 走った距離で減り、少ないほど速度が落ちる |

🔴 **1回の行動には秒数を与える**（ループ#1）。毎ティック行動させると
「1試合の奪い合い4,081回・走行191km」のように集計値が桁で狂う。
例外は出ず試合も成立するので、数字を相場と並べるまで気づけない。
→ `ACTION_CONTROL_TICKS` / `TACKLE_COOLDOWN_TICKS`。検査は `scripts/check_project.ts` の [2]。

🔴 **乱数・時刻は引数で受ける**（D-08）。モジュール関数の `random.*` は使わない。

### 一人一人が考えて動く（2026-09-30 オーナー指摘 → D-12）

> 「全体的に連動して動きすぎてる。オフザボールの時間に一人一人考えて動いてる感じがまったくない」

全員が毎ティック同じ式を解くと、**11人が塊で平行移動する**。例外は出ず試合も成立するので、
画面で見るまで誰にも分からない。5つで防ぐ。

1. **考え直す秒を選手ごとにずらす**（`DECIDE_INTERVAL_TICKS` ＋ 個人の `decide_offset`）
2. **決めた意思は次に考え直すまで持つ**。向かう先は一点に固定し、ボールを毎秒追い直さない
   （追うのは寄せ役・マーク役・こぼれ球だけ）
3. **向きは急に変えられない**（`TURN_RATE_RAD`・1秒で約49度まで）
4. **意思ごとに本気度が違う**（`EFFORT`）＝走る人と歩く人が混ざる
5. **攻守で陣形が前後する**（`BLOCK_PUSH_UP_M` / `BLOCK_DROP_M`）。前後の量は
   選手ごとのカバー範囲で割り引く（全員同じだけ動くと、また塊になる）

隠しパラメーターは「その行動を**選びやすさ**」として効く。重みを混ぜて1本の式にすると、
また11人そろった平均の動きに戻る。

🔑 検査は `tests/movement.test.ts`。**チーム共通の流れを差し引いた残り**を数える
（完全な塊なら0）。指摘前 0.585 → いま 0.78。

### 撃つかどうかと、入るかどうかは別（2026-09-30 オーナー指摘 → D-13）

> 「シュート出来る位置にいるのにシュートしない」

`撃つ = 0.015 + 1.00 × ゴール期待値` としていたため、12mで入る確率が10%なら
撃とうとするのも10%だった。実測で **6〜12mの判断2回すべてで撃たなかった**。
→ 撃つ気は**距離で直接**決める（`SHOOT_WILL_NEAR` / `SHOOT_WILL_PER_M`）。
   期待値は**入るかどうか**にだけ使う。

### 出す相手がいないなら出さない（同・D-14）

> 「意図的に相手にボールを渡してるような場面が多くある」

候補が1人でもいれば必ず最善の1人へ出していたので、囲まれた味方にも出していた。
さらに失敗したパスは、経路から4m離れた相手が**そのまま保持**していた。
→ `PASS_MIN_SCORE` を下回るなら出さない。奪取は進路上 1.8m 以内だけ、
   外はこぼれ球（取り合い）。実測で「相手がそのまま奪った」が 26.9% → 10.9%。

## 10. チーム戦術・チーム方針・監督の性格

ユーザーが試合前に設定できるのは、基本戦術・条件付きのチーム方針・監督の性格の3層。
これが非同期PvPにおける「試合中の指示」の代わりになる。

**基本戦術**

| 項目 | 選択肢 |
| --- | --- |
| line_height | 1〜5 |
| zone_width | 1〜5 |
| attitude | 守備的 / バランス / 攻撃的 |
| フォーメーション | 4-4-2 / 3-5-2 / 4-5-1 / 3-4-3 |

**チーム方針**：条件と行動のルールを最大5個。60ティックごとに上から判定し、最初に当てはまった行動を適用する。

| 条件 | 意味 | 行動 | 効果 |
| --- | --- | --- | --- |
| LEADING_LATE | リード中かつ75分以降 | LINE_DOWN | ラインを2段下げる |
| TRAILING_LATE | 負けていて70分以降 | PUSH_UP | ラインを2段上げ、攻撃的にする |
| OPP_GK_WEAK_KICK | 相手GKの kick が50未満 | HIGH_PRESS | 全員の press に +30 |
| OPP_HIGH_LINE | 相手の line_height が4以上 | THROUGH_BALLS | 裏へのパスを優先 |
| OWN_STAMINA_LOW | 味方の平均スタミナが40%未満 | LESS_PRESS | 全員の press に -30 |

条件と行動は自由に組み合わせられる（表の横並びは対応関係ではない）。

**監督の性格スライダー**（各 -2〜+2）

| スライダー | 左↔右 | 効果 |
| --- | --- | --- |
| style | 守備的↔攻撃的 | attitude の初期値に影響 |
| rigidity | 弾力的↔徹底的 | 徹底的ほどチーム方針が発動しにくい |
| substitution | 消極的↔積極的 | 積極的ほど早く多く交代（控え5人、交代3人まで） |
| selection | 安定感↔期待感 | **MVPでは値のみ保持、処理なし**（§12 の未決定） |

## 11. コマンド・出力・プリセット・テスト

| 用途 | コマンド |
| --- | --- |
| 遊ぶ | `npm run play` |
| 1試合 | `npm run sim -- match data/team_a.json data/team_b.json --seed 1` |
| 特訓の検証 | `npm run sim -- train --card running --times 20` |
| 全カードの一覧 | `npm run sim -- train-all` |
| 大量対戦 | `npm run sim -- batch --matches 200 --seed 1` |
| チームJSONの作り直し | `npm run sim -- presets` |

**試合ログ**（JSON）：時刻・種類（パス、奪取、シュート、ゴール、交代、方針の発動）・選手名。
最後にスタッツ（シュート数、支配率、パス成功率）と課題一覧。

**プリセット6チーム**：同じ初期能力の選手に違う特訓を20回ずつ行って作る。能力合計はそろえる。

| チーム | 特訓 | チーム方針 |
| --- | --- | --- |
| 走力型 | ランニング中心 | — |
| プレス型 | プレス中心 | HIGH_PRESS |
| パス型 | パス中心 | — |
| 裏抜け型 | ダッシュ中心 | THROUGH_BALLS |
| 堅守型 | マンツーマン中心 | LEADING_LATE → LINE_DOWN |
| バランス型 | 全カード均等 | — |

リーグ用に7チーム目「シュート型」を足し、**自チーム＋AI7＝8チーム**で2回戦総当たり14節。
🔴 `batch` の勝率表は要件どおり**6チームのまま**にする（リーグ用の追加に引きずらない）。

### 相場との照合の仕方（2026-10-01・ループ#5で作り直し）

`node scripts/measure.ts` が現実のサッカーの相場と照合している（出典はスクリプト内）。

🔴 **相場は「リーグの平均」なので、平均と比べる。**
   プリセット6チームは「1種類のカードだけ20回」という極端な型で、
   シュートだけ20回積んだチームと実在リーグの平均を直接比べても意味がない。
   どう調整しても6チームの幅が相場の幅より広くなり、**ゲーム側を壊さないと緑にならない**状態だった。

2段構えにしている。

1. **平均**が相場に入っているか ← ゲーム全体が現実的か
2. **どのチームも壊れていないか**（相場の幅1つぶん外れたら壊れている）
   ← これが無いと、平均だけ合わせて中身がめちゃくちゃでも緑になる

`KNOWN_RED` は **2026-10-01 のループ#5/#6 で空になった**。
増やすときは報告書に理由を書く（`tests/measure.test.ts` が空であることを固定している）。
