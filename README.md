# ドットサッカー育成ゲーム（MVP）

**ブラウザで遊べます。** 試合は右斜め後ろからの見下ろしで、22人のドット絵が動きます。

```bash
python scripts/build_web.py            # 配るものを web/dist に組み立てる
python -m http.server -d web/dist 8080 # → http://localhost:8080
```

端末から遊ぶこともできます。

```bash
python -m sim play
```

🔑 **試合の規則は `sim/`（Python）にしかありません。** ブラウザ版は Pyodide で
その Python をそのまま動かしています。JavaScript に写すとエンジンが2つに分かれ、
テストと検査が Python 側にしか無いので、どちらが正かが崩れるためです。

中身は3層になっている。

- **ゲーム層**（`play`）: 自チームを作り、8チームのリーグを14節戦い、試合で出た課題から
  特訓カードをもらって選手を育て、シーズンを越える。進行はセーブされる。
- **検証層**（`match` / `train` / `batch` / `scripts/measure.py`）: ゲームの核を数字で確かめる道具。
  1. **特訓の違いで選手の隠しパラメーターとタイプが変わり、試合中の動きが変わること**
  2. **大量の自動対戦で勝ちすぎるチームがなく、戦術の相性（じゃんけん関係）が生まれること**
  3. **試合のスタッツが現実のサッカーの相場に収まっていること**（出典つき）
- **画面層**（`web/`）: ブラウザの画面。**規則は1行も持たない**。
  Python が返した値を並べるだけ。

- 要件定義書（**正本**）: `docs/requirements.md`
  🔴 Downloads のドラフトはもう参照しない
- 矛盾への決着の経緯（D-01〜D-10）: `docs/decisions.md`（決定の理由はこちら）
- 正しさの定義書: `docs/phase0_correctness_definition.md`

環境: **Python 3.11 / 実行時は標準ライブラリのみ**（外部通信なし）
🔑 `ruff`（lint）と `mypy`（型チェック）は**開発ツール**なので使います。
   実行時の制約とは別物です。

## 遊び方（ゲーム層）

```bash
python -m sim play                        # セーブがあれば続きから
python -m sim play --save saves/b.json    # 別のセーブで遊ぶ
```

### 1回の流れ

1. **チームを作る** — チーム名 / 運の種 / フォーメーション / **初期育成の配分**
   （全選手に特訓20回。AIチームも同じ20回を受けた状態で開幕するので、
   配分だけがチームの個性になる。プリセットと同じ配分を選ぶこともできる）
2. **戦術を決める** — ライン高さ・守備幅・姿勢・フォーメーション・
   チーム方針（条件→行動を最大5個）・監督の性格スライダー4つ
3. **試合へ** — 同じ節の他会場も同時に消化される。
   スコア・得点者・スタッツ・**課題から得た特訓カード**が表示される
4. **選手と特訓** — カードを1枚（通常）か2枚（スペシャル）使って選手を育てる。
   タイプが変わると表示される。先発と控えの入れ替えもここ
5. **14節終わったらシーズンを締める** — 最終順位が記録され、
   AIチームも自分の型で成長して次シーズンへ

### メニュー

| | |
|---|---|
| 1 | 次の試合へ（全節終了後は「シーズンを締める」） |
| 2 | 選手と特訓（一覧・特訓・先発入れ替え） |
| 3 | 戦術を決める |
| 4 | 順位表と日程（残り日程・過去シーズンの成績） |
| 5 | セーブする（試合後・特訓後は自動セーブ） |
| 0 | セーブしてやめる |

リーグは **自チーム＋AI 7チーム = 8チーム、2回戦総当たりの14節**。
AIは要件定義書のプリセット6チーム＋リーグ用の「シュート型」。
セーブは `saves/default.json`（書き込みは別名に出してから置き換えるので、
途中で落ちても前のセーブは壊れない）。

## 検証層の使い方

```bash
# チームJSONを作り直す（data/ に6プリセット + team_a / team_b）
python -m sim presets

# 1試合。スコア・スタッツ・課題を表示し、logs/ にJSONログを保存
python -m sim match data/team_a.json data/team_b.json --seed 1

# 特訓の検証。1回ごとの隠しパラメーターとタイプ、変化した回数
python -m sim train --card running --times 20
python -m sim train --card man_mark --card running --times 20   # 2枚＝スペシャル
python -m sim train-all --times 20                              # 全7カードの一覧

# 大量対戦（プリセット6チーム総当たり・各組200試合＝3,000試合）
python -m sim batch --matches 200 --seed 1
python -m sim batch --matches 20 --seed 1 --workers 4            # 軽く回すとき

# 検査
python -m unittest discover -s tests      # 自動テスト73件（うちゲーム層34件）
python scripts/check_project.py           # 提出前検査（ダミー値・定数の不変条件・実データ）
python scripts/measure.py 3               # 平均スタッツの実測（数値が現実離れしていないか）
```

カード名: `running` / `man_mark` / `press` / `pass` / `dash` / `shoot` / `zone`

## フォルダ構成

```
sim/
  constants.py   調整可能な値（全部ここ）
  model.py       選手・チーム・戦術・タイプ判定
  training.py    特訓カード・スペシャル・課題の発見
  engine.py      試合エンジン（5400ティック）
  presets.py     AIプリセット・自チームの初期生成
  batch.py       大量対戦と勝率表
  league.py      リーグの日程と順位表（純関数）
  career.py      ゲーム進行の状態と規則（入出力を持たない）
  ui.py          対話画面（入出力を注入できる）
  __main__.py    コマンド入口
data/          チームJSON（プリセット6 + team_a + team_b）
tests/         自動テスト（test_sim.py 39件 / test_game.py 34件）
scripts/       検査と実測の道具
docs/          決定事項・正しさの定義書
logs/ out/ saves/   試合ログ・勝率CSV・セーブ（生成物・gitignore）
```

`career.py`（規則）と `ui.py`（画面）を分けているのは、**対話を挟まずにテストから
1シーズン最後まで歩けるようにする**ため。`play_game(inputs=[...])` に入力を渡すと
無人で全画面を通せる（実際にテストがそうしている）。

バランス調整に触る値は**すべて `sim/constants.py` の1箇所**にある。

## 完成条件② batch 3,000試合の勝率表

`python -m sim batch --matches 200 --seed 1` — 6チーム総当たり15組 × 各200試合 = **3,000試合 / 158.7秒**
（1試合53ms・ホームとアウェーを1試合ごとに入れ替え）

表の数字は**行のチームから見た勝率**（引分は0.5）。

| | 走力型 | プレス型 | パス型 | 裏抜け型 | 堅守型 | バランス型 | 全体勝率 | 戦績 |
|---|---|---|---|---|---|---|---|---|
| 走力型 | — | 0.233 | 0.087 | 0.190 | **0.652** | 0.185 | **27.0%** | 147勝245分608敗 |
| プレス型 | 0.767 | — | 0.640 | 0.720 | 0.507 | 0.605 | **64.8%** | 418勝460分122敗 |
| パス型 | **0.912** | 0.360 | — | 0.593 | 0.295 | 0.360 | **50.4%** | 338勝332分330敗 |
| 裏抜け型 | 0.810 | 0.280 | 0.407 | — | 0.388 | 0.290 | **43.5%** | 297勝276分427敗 |
| 堅守型 | 0.347 | 0.492 | **0.705** | 0.613 | — | 0.468 | **52.5%** | 324勝402分274敗 |
| バランス型 | 0.815 | 0.395 | 0.640 | 0.710 | 0.532 | — | **61.9%** | 501勝235分264敗 |

### 判定

- ✅ **要件を満たす**: 全体勝率が70%を超えるチームは**無い**（最高はプレス型の64.8%）
- ✅ **じゃんけん関係が実測で出ている**:
  **走力型 → 堅守型（0.652） → パス型（0.705） → 走力型（0.912）** の循環。
  最弱の走力型が、上位の堅守型に65%で勝つ。総合力の一本道になっていない。
- ⚠️ **未達**: 走力型 27.0% が**下限30%を下回る**（詳細と対処案は下記）

### 走力型が弱い理由（オーナー判断が必要な残課題）

走力型は `stamina` にだけ100を積んだチーム。他の5チームはそれぞれ
`speed` / `technique` / `physical` を100まで上げており、これらは
**シュート・パス・ドリブル・奪い合いの判定に直接入る**。一方 `stamina` は
「疲れにくさ」だけで、判定式に直接は出てこない。**能力の格が揃っていない。**

試した対処と結果（すべて実測）:

| 試したこと | 結果 |
|---|---|
| speed の幅を狭める（2.2〜7.4 → 3.6〜6.6 m/s） | プレス型 72.5% → 65.0%。**採用** |
| 疲労を技術にも効かせる（`Actor.eff`） | プレス型 80.5% → 72.5%。**採用** |
| 体力の総量を広げる（30 + 2.2×stamina） | わずかに改善。**採用** |
| 立ち止まっている間に体力が回復する | **全チームが元気なままになり、バランス型が83.5%に跳ねた。不採用** |

対処案（要判断）:

- **案A**: ランニングカードの隠しを `overlap` から別のものに変える。
  現状 `overlap` はDF・MFを前に出すので、走力型は**自分から守備を薄くしている**（被シュート最多）。
- **案B**: `stamina` を一次能力にする。例: スタミナが高いほど奪い合いの継続力が上がる等、
  判定式に直接入れる。
- **案C**: 走力型にチーム方針を与える（要件定義書のプリセット表では走力型の方針は「—」）。

いずれも**ゲームデザインの選択**なので、実装前にオーナーの判断を仰ぐ。

## 設計上の約束（崩さないこと）

| 約束 | 理由 |
|---|---|
| 乱数は `random.Random` のインスタンスを引数で渡す | モジュール関数を使うとシード固定が破れる。テストで機械的に検出している |
| タイプは保存せず隠しパラメーターから導出する | 保存すると「同期を忘れる」故障が生まれる。JSONにタイプがあったら検査で落ちる |
| バッチのシードは `seed_for()` で導出する | 並列度・実行順が変わっても同じ試合には同じシードが渡る |
| `PRESS_STANDOFF_M > TACKLE_RADIUS_M` | 内側にすると全員が毎秒奪い合いに参加する（実測で1試合4,081回になった） |
| 1回の行動に秒数を持たせる（`ACTION_CONTROL_TICKS`） | 毎ティック判断させるとスタッツが現実離れする |
| run_space は相手最終ラインの**手前**まで | 越えるとオフサイドを免れて1試合6.6得点の壊れた強さになった |
| 勝率は床と天井の両方を警告する | 天井だけ見ると「弱すぎるプリセット」を見逃す |
| 自チームも必ず初期育成20回を受けてから開幕する | AIは20回育った状態。素で始めるとチーム合計で840点の差がつく（実測: 自3270 / AI4110） |
| 個性（能力の配分ずらし）は**特訓のあと**に付ける | 先に付けると +60 される能力が106になって上限で切られ、能力合計が減る |
| リーグは偶数チーム | 奇数だと必ず1チームが休みになり消化試合数が揃わない。検査で止めている |
| セーブは別名に書いてから置き換える | 書き込み中に落ちても前のセーブが残る |
| セーブの欠損・版違い・未知のカードは**エラーにする** | 既定値で埋めると壊れたデータのまま遊ばせることになる |
| `batch` のプリセットは6チームのまま | リーグ用に7チーム目を足したが、提出済みの勝率表の前提を変えない（検査で固定） |

## バランスについて（オーナー方針: 後から調整する）

2026-09-30 時点の実測は上の勝率表のとおり。**調整はすべて `sim/constants.py` の1箇所**で行う。
ゲーム層を足しても `batch` の数字は変わらない（検査で固定している）ので、
定数を変えて `python -m sim batch --matches 20` を回せば、調整の効果をすぐ測れる。

ゲーム層で新しく効くようになった調整つまみ:

| 定数 | 意味 |
|---|---|
| `AI_TRAININGS_PER_SEASON` | AIチームが1シーズンで選手1人に行う特訓回数（プレイヤーの成長速度との釣り合い） |
| `LEAGUE_DOUBLE_ROUND` | 2回戦総当たり（14節）か1回戦（7節）か |
| `MAX_CARD_STOCK` | 同じカードの所持上限 |

既知のバランス上の癖（未調整・要件の合格条件には触れない）:

- AIチームは**見える能力が既に上限100**に達しているので、シーズンを越えても伸びるのは
  隠しパラメーターだけ。プレイヤーは伸びしろが残っている能力を育てられるため、
  シーズンを重ねるとプレイヤー有利になっていく。
- 走力型の全体勝率 27.0%（詳細は上記）。

## MVPに含まれないもの

- **NFT・賭け要素**: 賭けで得たゲーム内通貨が外部取引可能なNFTにつながる構造は
  賭博罪の確認が必要（要件定義書 §12）。**弁護士確認まで実装しない。**
- **ドット絵・グラフィカルな画面**（今はコマンド上の対話画面）。
  要件定義書 §12 に「名称・キャラクター・ドット絵・UIはカルチョビットから独立した
  オリジナルにする」が未決定として残っているため、絵と画面はその決定待ち。
  試合の中身（座標・イベント）は1秒ごとに全部出ているので、描画層は後から載せられる。
- **非同期PvP・サーバー処理**（今はローカルのリーグ戦）。試合は決定論なので土台はできている
- `selection`（安定感↔期待感）スライダーの効果 — 要件定義書どおり値のみ保持
